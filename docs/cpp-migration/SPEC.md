# Genko Studio C++移行・改善仕様

版: 1.1 / 作成日: 2026-10-01 / 更新日: 2026-10-04 / 状態: 承認済み計画に沿って移行中

## 1. 決定事項と適用範囲

- **採用構成はC++20＋Qt 6。比較用のPython改良版、捨てる試作、言語選定のA/B開発は作らない。** 各工程で書くコードは最終製品の一部とする。
- 目標はGUI、描画、編集、保存、書き出し、CLI、HTTP、MCPをC++へ移行した製品。Python製本体を内部呼び出しして動くものを完成版としない。
- 移行と同時に、本書の保存保護・性能・導入・写植・PSD文字・紙質・画面・AI接続の改善を実装する。CSP全機能の複製や売上保証を目標にはしない。
- 既存のPython版は利用中の安定版・移行元として保持する。新機能を二重実装せず、C++版だけを開発する。既存ファイルの契約確認・入出力互換試験は、禁止する「別案を開発して性能を比較すること」には当たらない。
- 当初の計画作成後、利用者の指示で実装・検証を開始した。2026-10-04の整理指示により検証頻度をVALIDATION.mdへ一本化する。既存版の置換、本番原稿の使用、新費用、権限変更は別の承認境界を維持する。

## 2. 現行基準と仕様の優先順位

基準コミット: `1b7b1d7030d4188d7ebd5e398d010b3ed98b220f`。

現行READMEの正式対象はWindowsとLinux。手描き、コマ、写植、レイヤー、トーン、素材、3D、アニメーション、各形式の入出力、外部AIとの制作工程を引き継ぐ。古い設計文書にない機能も、現行実装に存在するものは移行対象に含める。

静的棚卸しは`baseline-inventory.json`を正本とする。操作スキーマ168種、MCP道具41種、MCPリソース4種、Pythonモジュール146本、試験ファイル118本、テスト関数定義880個を抽出した。これは実行ケース数でも合格数でもない。以前の954ケース中952成功・性能2件未達、選択試験33件成功とは区別する。

優先順位は、今回の明示指示→本仕様と受入基準→固定した現行データ・公開インターフェースの契約→現行の設計メモ。`CSP_GAP.md`等の「対応済み」記述だけで実動作の合格を扱わない。既知の不具合まで互換動作として再現しない。

## 3. 製品構成

### ARCH-01 本体と言語

- C++20、Qt 6 Widgetsを使用。CMake＋Ninja、CTest＋Qt Testを標準構成とする。Qtの採用パッチ版、コンパイラ、依存版・取得元・ハッシュをM0で固定する。最新という理由だけで開発途中に更新しない。
- Windows 11 x64、Ubuntu 24.04 x86_64を最初の正式対象とする。OS別検証と実機代替の範囲はACCEPTANCE.md §6に従う。macOS・ARM・モバイルは本移行の正式対応範囲外であり、非対応化の断定ではない。
- 配布物はPython、uv、pip、開発用コンパイラを利用者に要求しない。テスト・文書生成のPythonは開発環境だけで使用可。
- 外部AIクライアント、利用者登録のアップスケーラー、既存Pythonプラグインは外部拡張として区別する。Pythonプラグイン互換の条件はCOMP-04に従い、本体のPython残置の口実にしない。

### ARCH-02 モジュールと依存方向

`native/`以下に次の最終製品モジュールを置く（ここでは配置の仕様だけを定義する）。

- `core/`: Document、Page、Frame、Layer、Stroke、Text、ID、単位、CommandBus、権限、変更集合。GUIに依存しない。
- `storage/`: 旧形式読込、v4保存、素材ストア、排他、トランザクション、履歴、復旧。
- `render/`: 描線、タイル、レイヤー合成、トーン、効果、3D、色管理。画面と出力で同じ内容モデルを使う。
- `text/`: 縦書き、字体処理、禁則、ルビ、字間、フキダシ、グリフ配置。
- `formats/`: PSD/PSB読込、PSD出力、PNG/TIFF/PDF/EPUB等の出力。外部入力を検証してcoreへ渡す。
- `studio/`: 企画・脚本・依頼・候補・承認・相談・共同編集・制作順序。
- `api/`: CLI、HTTP、MCP、設定変換、エラー整形。core/studioの同じコマンドを呼ぶ。
- `app/`: Qt画面、IME、ペン、ショートカット、案内、アクセシビリティ。
- `tests/`、`packaging/`: 契約・受入試験、配布。`genko`一つのCLIから`app`、`mcp`、`serve`等を起動できる構成とする。

appやAPIからJSONを直接書き換える経路は禁止。変更はCommandBus→検証・権限判定→変更集合→保存サービスへ集約する。描画途中の一時線は可逆なプレビューとし、線の確定時にコマンド化する。

### ARCH-03 スレッド・所有権

- QWidget/QPixmap等のGUI操作はメインスレッドだけ。ワーカーは独立した画像バッファと不変スナップショットを扱い、結果をキューで返す。
- 原稿変更は一つの実行列で順序付ける。文書リビジョンと描画世代IDを持ち、古い結果は画面へ適用しない。ワーカーから生ポインタで編集モデルを変更しない。
- 保存・出力・重いフィルター・細部レンダリングはGUIスレッドを占有しない。入力受付、進捗、取消を継続する。単にスレッドに移しただけで完了扱いにしない。
- RAII、所有権が明確なスマートポインタ、境界チェックを基本とする。画像寸法・演算のオーバーフロー、use-after-free、データ競合を検査する。

### ARCH-04 描画と依存ライブラリ

- CPUタイル描画を必須経路とし、専用GPUを起動条件にしない。表示合成でQtのGPU機能を使っても、CPU代替経路と同じ原稿結果を保証する。
- FreeType＋HarfBuzzを文字の字体処理候補ではなく採用構成とし、縦書き・ルビ配置はGenkoのC++レイアウト層で扱う。QTextEditだけで原稿組版を代替しない。
- 色変換はLittle CMS、画像形式はQtの利用可能なコーデックとlibpng/libjpeg-turbo/libtiff/libwebp、圧縮はzlibを用途別に使用。JSONは64bit整数を保てるライブラリを使用し、QJsonの数値変換でID・リビジョンを丸めない。
- 既存PSDの読書き仕様はC++へ移し、PSDの文字拡張を追加する。Pythonのpsd-toolsを製品実行時の変換器にしない。
- 動画出力に外部FFmpegを使う場合はライセンスと対応codecを明記する。自動ダウンロード、有料codec契約は行わない。現行機能の外部依存を黙って削除しない。

### ARCH-05 費用・ライセンス

QtはLGPL利用条件を満たす動的リンク構成を基本とする。MITの本体と第三者ライセンスは別管理。ライセンス文、対応ソースの提供義務、ライブラリ差替え・再リンク条件、変更箇所を確認し、GPL専用モジュールを無断追加しない。依存物・フォント・アイコンのSBOMを配布する。商用Qt、署名証明書、新クラウド、新API課金が必要ならその項目だけ停止して承認を求める。

## 4. 原稿・互換性・保存

### DATA-01 旧原稿を壊さない移行

- `.genko`は拡張子付きディレクトリであり、単一ZIPと誤認しない。旧v1/v2/v3を読めるC++リーダーを用意する。
- 初回は旧writerとGCを停止し、既存writerと協調する排他の下で全体の固定コピーを取得する。原本が使用中、協調排他を確保できない、収集途中の変更を検出した場合は公開せず停止する。固定コピーのmanifest・履歴・監査・履歴から到達する素材までハッシュを固定してから変換する。原本の内容・設定・承認記録は書き換えない。既存ロックファイルの排他取得と内容変更を区別する。
- 固定コピーを読み取り専用で解析し、欠損素材・未知機能・不足フォントを一覧化。利用者が選んだ別の`.genko`へ変換する。稼働中の原稿ディレクトリを直接走査した結果だけで移行成功としない。
- C++版の書込み形式はv4。`version:4`、読取最低版、writer情報、拡張機能識別子を持つ。旧版が新原稿を書き戻して情報を落とすことを避ける。v4をPython版で編集する運用は提供しない。
- 旧ID、mm単位、ページ順、コマ木、本文、改行、ルビ、レイヤー順、素材、筆圧、承認・actor・sessionを維持する。旧履歴は不変の保全領域へ原本バイトとハッシュ参照ごと保存する。旧スナップショットのハッシュ→変換済みv4状態IDの対応表と移行境界を作り、v2の相対参照を含む履歴から到達する素材も取り込む。
- 旧履歴へのUndo/Redoは対応表から内容を取り出し、権限を再検証した**新しいv4 transaction**として確定する。旧project.jsonをそのまま書き戻さず、v4→v3等への巻戻しを禁止する。変換前後の監査を連結するが、過去の承認を新規承認として作り直さない。
- 将来の未知フィールドは拡張領域へ保持。未実装の表示・編集意味を持つ場合は該当操作または原稿を読み取り専用にし、空として保存しない。

### DATA-02 素材・数値・スキーマ

- `assets/<先頭2桁>/<sha256><suffix>`と`sha256:<64桁hex>`を引き継ぐ。読込時は参照形式、パス、必要に応じ実バイトのハッシュを検証する。
- 既存の画像・スナップショットのバイト列を保存する。JSONを再整形して既存ハッシュを流用しない。新規JSONはUTF-8、固定キー順、ロケール非依存数値、LFとし、テストベクトルで仕様固定する。
- 筆跡のpacked little-endian float64とbase64を正しく読む。32bit化による座標・筆圧の精度低下、NaN/Infinityの混入、リビジョンの丸めを禁止する。
- 書式拡張は`docs/cpp-migration/schema-v4.md`へM1で確定する。必須項目、既定値、単位、範囲、未知フィールド、前後互換、JSON例を定義してから本番用writerを実装する。

### SAVE-01 保存状態と終了保護

表示状態は「保存済み」「未保存」「保存中」「保存失敗」「復旧用コピーのみ」の5種。保存失敗時は理由・保存先・最後の成功時刻を表示し、再試行、別名保存、復旧コピー作成を選べる。復旧コピーだけの成功を通常保存済みにしない。

未保存・保存失敗・保存中に閉じる、原稿切替、アプリ終了を行った場合は既定で停止する。「保存して閉じる」は保存成功後のみ終了。「保存せず破棄」は明示確認を要し、キャンセルが安全側の既定。例外が発生しても画面とメモリ内の原稿を維持する。

保存中に追加した編集は別世代としてdirtyを維持する。古い保存完了通知で新しい編集を保存済みにしない。OS強制終了・電源断で未永続化の編集を完全保証するとは表示しない。

### SAVE-02 原子的な確定と復旧

同一原稿の書込みはOS排他とbase_revision検証で直列化する。v4の公開revisionは単調増加の永続化世代であり、Undo/Redo、復旧内容の採用も新しい世代を割り当てる。復元対象のhistory_state_idと世代は別で、過去のrevisionを再利用しない。base_revisionにはこの世代を使い、編集→Undo後に旧クライアントが一致するABA競合を防ぐ。POSIXのflockとWindowsの既存互換範囲ロックを扱い、単なるQLockFile置換で既存版との排他を破らない。競合時は相手の変更を無言で上書きしない。

保存手順は次の通り。

1. 対象リビジョンの不変スナップショットを作り、変更素材と履歴用before/afterを一時ファイルへ出す。
2. 新素材をflushし、同一ボリューム内のrenameで確定する。既存ハッシュの内容を書き換えない。
3. transaction_id、before/after、base_revision、actor、必要素材を持つprepare記録を永続化する。
4. `project.json`を一時ファイル→原子的置換で確定し、履歴と承認監査をtransaction_idで重複なく記録する。
5. commit記録と必要なOS同期が成功してから、該当リビジョンを保存済みとして通知する。

起動時、保存失敗時、および次の更新・Undo・保存の前に、排他下で未完了transactionと末尾破損ログを検査し、最後の整合した確定点へ復旧する。同一transaction_idの再試行は一度だけ確定し、既に確定した場合は同じ確定世代を返す。修復できるまでは書込みを止め、画面のdirty状態とディスクの確定世代を再照合する。projectだけ更新済みならprepareから履歴を修復し、同じ承認を二重記録しない。素材不足なら旧整合点を保持して読取専用とする。復旧できないときに空原稿で上書きしない。ファイルシステムが永続化を保証しない場合は警告し、ネットワークドライブやクラウド同期先を初期の安全保証範囲に含めない。

### SAVE-03 自動保存・履歴・GC

- 入力を止めない自動保存と、別の復旧領域へのチェックポイントを設ける。既定は変更の休止後2秒、連続作業時は最大10秒で復旧点作成を開始する。実際の成功リビジョン・時刻を表示する。
- 保存失敗中は復旧点の有無を知らせ、原稿領域も復旧領域も書けなければ明示警告する。成功していない編集を保護済みと呼ばない。
- 原稿・復旧点・Undo/Redo・進行中出力・transactionが参照する素材はGCしない。GCは排他、dry-run、対象表示を備え、初期移行時には自動実行しない。
- actor/sessionごとのUndoと人間の承認変更の制約を維持する。履歴復元による承認回避を拒否する。
- 既知の制限（2026-10、M5 出口）: 画面の変更のうち本の中身を変えるもの（線・台詞・ページの操作など）が保存を待つ間に、別の書き手（AI の `apply_ops` など）がページの番号と ID の対応を変える（並べ替え・削除・挿入）と、その変更は番号のまま別のページに当てず、ID で付け直すこともせず、競合（`rebase_conflict`）として未保存のまま残す（画面のメモリーと復旧用コピーにはある）。人がその変更を元に戻すまで、後の変更も原稿に書かない。コマの選択（`select_frame`）だけは本の中身ではないので付け直す（COMP-01a）。
- 既知の制限（2026-10、M5④）: C++ 版の原稿（v4）には旧版（Python 版）の `genko gc`・`genko undo` を使わない。旧版の gc は v4 を断らず、v3 の journal が名指すものだけを残すため、1 日より古い v4 の履歴の状態・状態だけが名指す素材・変換した旧履歴を消す（旧版の undo は v4 の journal を読めずに止まる）。消された後も C++ 版は原稿を今の中身のまま開き、保存・gc・修復を続け、消えた所より前に戻る Undo（その状態へ進む Redo）は何も書かずに `history_missing` で断り、`genko doctor` が消えたものと Undo が戻れる所までを報告する（schema-v4 §8）。

## 5. 機能を落とさない移行

### COMP-01 操作・画面の網羅

168種の操作を最低限の棚卸し単位にし、名前だけでなく引数、既定値、成功結果、失敗時の無変更、Undo、保存再開、GUI入口を対応付ける。M0で実dispatchとスキーマ差分、GUI専用機能、設定、素材・ブラシ・ワークスペース、ショートカットを追記する。移行対象の省略は利用者の明示承認なしでは認めない。

#### COMP-01a 現行の不具合を再現しない変更（実装で確定したもの）

§2「既知の不具合まで互換動作として再現しない」に従い、原稿の破損・無限ループ・二重参照・安全の問題につながる現行の挙動は、C++ 版では入力を拒否する（原稿は変えない）。出力の見た目と数値の細部は現行と同じにする。

| 現行の挙動 | C++ 版 | 工程 |
|---|---|---|
| 高さ 0 のコマで読み順の計算が止まらない | そのコマ単独で行を作って終える | M1 |
| `raster_relpath`・素材参照が原稿フォルダーの外を指せる | 読まずに報告し、読取専用で開く | M1 |
| 欠けた素材・ページより下の未知キー・配置画像層の筆跡が保存で黙って消える | 報告して読取専用で開き、保存を拒否 | M1 |
| 型の合わない値・NaN/Infinity・64bit を超える整数 | 既定値か null に置き換えて報告し、読取専用。`--accept-repairs` で変換 | M1 |
| op の NaN/Infinity | 拒否 | M1 |
| journal の読込が U+2028 で行を分ける | `\n` だけで分ける | M1 |
| `reorder_layers` に同じ id が重複すると同じ層が 2 か所に入り、片方の編集が他方に出る | `ids must not repeat` で拒否 | M2 |
| `reorder_layers` の order に無い層が消える（空の order で全部消える、未知の id は無視） | `order must list every layer of the page once` で拒否 | M2 |
| 存在しないページへの `lock_page`／`unlock_page` が成功する | `no page <n>` で拒否 | M2 |
| `select_frame` がページに無い `frame_id` を受け付ける | 拒否 | M2 |
| `set_layer` の `parent` に任意の値を保存する | ページのフォルダー層の id か null だけ受け付ける | M2 |
| `for_pages` の `pages` の文字列を 1 文字ずつのページ番号として読む | `all`・`body`・整数の配列だけ受け付ける | M2 |
| 巨大な座標でメモリが尽きるまで処理が続く | 1000 万ステップで打ち切ってエラー | M2 |
| `delete_tone` がトーン以外の層も削除する | `layer <id> is not a tone layer` で拒否 | M3 |
| `pose_mannequin` が人形以外の 3D オブジェクトの寸法・姿勢を書き換える | `3D <id> is not a mannequin` で拒否（一括操作の他の変更も保存しない） | M3 |
| モデルの循環ノード・巨大な頂点数や面、トーン・効果線・定規の巨大な反復 | 共通の `core/limits.hpp` の上限で拒否 | M3 |
| トーンの勾配角度に文字列の `inf`・`nan` 等を保存し、後の描画が失敗する | 数値変換後の勾配角度も有限性を検査し、保存前に拒否 | M3 |
| 定規の点数計算で int64 の飽和値へ加算する／有限入力から非有限の輪郭ができ、ストロークとして保存される | 加算前に共通の点数上限を検査／新たに作る点の有限性を保存前に検査して拒否 | M3 |
| `lt_convert` がロック済みの出力先層に線を追加できる | `the layer is locked` で一括操作ごと拒否し、前置変更も保存しない | M3 |

### COLOR-02 CMYK・Lab のページ（C++ 版。利用者の決定 2026-10-13）

COLOR-01 の CMYK・Lab での編集。ページごとに色モード（RGB・CMYK・Lab）と精度（8・16 bit）を持ち、CMYK は ICC プロファイルを原稿に埋め込む。形式は schema-v4.md の「色モード（color-mode@1）」。CMYK・Lab のページでもページの機能を全部使える（工程の群ごとに統合する。まだ統合していない機能は `not_yet_ported` で断り、黙って RGB で描いたり変えたりしない）。RGB のページは今までどおり（Python 版と同じ画素）。

- **合成**: ページの色空間のまま合成する（RGB を通さない）。紙はインキなし（CMYK）・L 100（Lab）。不透明度・マスク・クリップは RGB のページと同じ形でインキの値に掛ける。
  - CMYK の描画モード: 各版を (1 − インキ) にして高精度の合成と同じ式で混ぜ、戻す（Photoshop の CMYK と同じ考え。乗算はインキが増える）。色相・彩度・カラー・輝度は (1 − C, 1 − M, 1 − Y) を RGB として式を当て、K は色相・彩度・カラーでは下の層の K、輝度では上の層の K。
  - Lab の描画モード: 符号化した値（L/100、(a+128)/255、(b+128)/255）の各版に式を当てる。使えるのは通常・乗算・スクリーン・オーバーレイ・加算・焼き込み（リニア）・ソフトライト・ハードライト。ほかのモードは Lab のページでは使えない（その op を断り、その層を持つページを Lab にする変換も断る）。
  - 色のページなので、モノクロの仕上げ（灰色を網点に）はしない。トーンは RGB のカラーのページと同じく網点にせずその濃さで描き、色は下の規則でインキに当てる（黒のトーンは K だけ、Lab は L）。補正レイヤーは下の「フィルターと補正」のとおり合成する。
  - 要素の色（線・塗り・文字・フキダシ・枠線・効果線・トーンなど）は RGB のまま持ち、schema-v4 の規則（ページの色の表 → 既定の墨と白 → 灰色は K だけ → プロファイルで変換）でインキに当てる。8 bit で描く要素は、黒と白の 2 枚の紙に描いて各画素の被覆と色を取り出し、その色をインキに当ててから合成する（色の表の色と灰色は正確。2 つの色の境目のアンチエイリアスの画素は変換した色）。
- **表示**: 合成したインキを sRGB にして画面・サムネイル・プレビュー・`genko render`・MCP の絵に出す（CMYK はページのプロファイルから、Lab は D50 から。相対的な色域を維持、黒点補正）。画面だけの印（下描きの色・ガイド・3D・定規・折り目・オニオンスキン）は表示の上に描く。「CMYK で見る（色校正）」は RGB と Lab のページに掛かり、CMYK のページはもともとインキの表示。
- **変換**（op `set_color_mode`。C++ 版だけの op、公開の `genko schema` は Python のまま）: `{"op": "set_color_mode", "page": int?（無ければ全ページと本の既定）, "mode": "rgb"|"cmyk"|"lab", "depth": 8|16?（既定 8）, "icc": "<ICC の base64>"? か "profile": "sha256:…"?（CMYK で必須。本が持つプロファイル）, "intent": "perceptual"|"relative"|"saturation"|"absolute"?（既定 relative）, "gray": "profile"|"k"?（既定 profile）, "default": bool?（ページを指したときも本の既定にする）}`。
  - 画素レイヤー（8 bit の PNG・高精度の画素・GKIR）を新しい色空間の GKIR に変換する（RGB へは `depth` 8（既定）なら PNG、16 なら高精度の u16。高精度の画素が持てない層の設定なら断る）。RGB → CMYK はプロファイル（意図・黒点補正）、`gray: "k"` ならちょうど灰色（r = g = b）の画素は K だけ（K = 1 − v/255。線画向け）。CMYK → CMYK（別のプロファイル）は K を保つ変換（Little CMS の preserve K only）。CMYK ↔ Lab、RGB ↔ Lab も Little CMS。透明度とマスクはそのまま。8 ↔ 16 bit は値を量子化し直す。
  - 要素の色は RGB のまま変えない（RGB に戻すと色の表は無くなり、要素は RGB の色で描かれる）。
  - Undo・Redo・保存・履歴は他の op と同じ。変換できないもの（Lab で使えない描画モードの層など）があれば何も変えずに断る。
- **色の表**（op `set_inks`）: `{"op": "set_inks", "page": int?（無ければ CMYK・Lab の全ページ）, "inks": [[[r, g, b], [v…]], …], "replace": bool?}`。RGB の色を正確なインキに当てる。画面の色の窓で CMYK・Lab の値を選ぶと、その色の表示用の RGB（変換して丸めた値。同じ RGB が別のインキに使われていれば 1 ずらす）を要素に、組を色の表に入れる。
- **書き出し**:
  - PDF・TIFF: 色が「自動」か「CMYK」なら、CMYK のページはインキの値のまま（8/16 bit）、そのページのプロファイルを埋め込む（書き出しの ICC は RGB のページの変換だけに使う）。Lab のページは「自動」で Lab のまま（PDF は `/Lab`、TIFF は CIELab）、「CMYK」では書き出しの ICC で変換。「RGB」「グレー」「白黒」は表示の sRGB から今までどおり。
  - PSD: CMYK のページは CMYK（色モード 4、8/16 bit、プロファイルを埋め込む）、Lab のページは Lab（色モード 9）で、レイヤーもインキで書く。編集可能な文字（PSD-01）も同じく書き（群D）、文字の層の画素はインキ、グループの記録はページの版の数。CMYK のページの文字の色は規則のインキ（EngineData の FillColor Type 2: α・C・M・Y・K）、縁取り（lfx2）の色は CMYC（%）。Lab のページの縁取りは LbCl、文字の色は RGB（Type 1。Lab の Type は確かめられない）。Photoshop での確認はしていない（psd-tools とこのビルドの読み手で照合）。
  - PNG・WebToon・SNS・EPUB・Kindle・strip・layers・アニメーション・印刷: 表示の sRGB。入稿セットは TIFF がインキのまま、PNG が sRGB。CMYK・Lab のページを sRGB にして書いたときは、書き出しの返事に `notes`（「CMYK・Lab のページ N ページは…画面の色（sRGB）から変換して書き出しました」）を付けて知らせる（黙って変換しない）: CLI（JSON の `notes`、ふつうの出力では標準エラー）、MCP の `export`（`notes`）、HTTP API の `/v1/export`（`notes`）、正式な書き出し、書き出しの窓とタイムラインの動画の書き出し（知らせの文）。タイムラプスは記録した履歴の絵なので対象外。
- **画素の操作**（工程の群B、`render/ink_edit`）:
  - 画素を消す・動かすだけの操作はインキの値のまま直接扱う（高精度の層と同じ）: 消しゴム（`erase`・`erase_raster`。ぼかし・ざらつきは 8 bit の消しゴムと同じ形で α を減らす。「線全体」「交点まで」は RGB のページと同じく線だけで画素は消さない）・範囲の削除（`delete_area`）・変形とワープ（`transform_area`。範囲の画素を持ち上げ、α を掛けたインキで再標本化して置く）・インキの断片の貼り付け（`paste`。画面のコピーは CMYK・Lab のページで範囲のインキを断片として持ち、同じ色モード・精度・プロファイルのページのペイントレイヤーへ、回さない貼り付けならインキのまま置く。ほかは表示の絵として貼る）・判型の変更（`set_page_spec`。古い枠から新しい枠へ 200 dpi・バイリニア）。道具が触れない画素は 16 bit の値のまま、動かした画素はそのインキのまま。
  - 結合と変換（`merge_down`・`merge_layers`・`merge_visible`・`convert_layer` のペイントへ）は、結合する層を op の前の設定のままページの合成と同じ形でインキで合成し直す（`render::composite_ink_layers`。透明から合成し、どの層も無い所は透明のまま。層の順・不透明度・描画モード・クリップ・紙は 8 bit の結合と同じ取り方）。
  - 新しい色を描く・混ぜる操作は、op の前に対象の層（ページ全体を合成する操作・層を作る操作ではそのページのインキの層すべて）を表示の絵（sRGB の 8 bit RGBA。RGB のペイントレイヤーの PNG）にして今までの操作に渡し、op の後でインキに戻す: 色混ぜ・ゆがみ（`smudge`・`liquify`）・塗りつぶし・グラデーション・図形・塗り残し（`flood_fill`・`gradient_fill`・`add_shape`・`fill_gaps`）・定規から（`ruler_to_layer`）・ライトテーブル（`lt_convert`）・3D から（`render_prims`・`trace_prims`）・高精度の画素（`put_color_raster`）。貸した層に op が絵として置いたもの（色混ぜが変えた範囲の絵など）は貸した絵に描いてから戻す。戻し方: op が色を変えなかった画素（同じ場所で 1 チャンネル 2 以内の変化を含む）はその画素のインキのまま（α も変わらなければ 16 bit のまま）。変わった画素は、色の表の色はそのインキ、貸した層が見せていた色はそのインキ（そのまま写った色はインキのまま）、Genko の墨・白と規則が見せる色（墨・K だけの灰色・インキなし）は規則のインキ、ほかの灰色は規則（K だけ。Lab は L）、見せていた色から 1 チャンネル 2 以内の色（α だけ変わった画素の丸め）はその色のインキ、残り（混ぜた色・新しい線のふち）はプロファイル。高精度の RGB の画素はプロファイルで。
  - op がペイントレイヤーに絵として置いたもの（表示の絵として貼った絵・素材・動かした範囲の絵）は、高精度の層と同じくその場でインキに描く（色はページの規則）。
  - 既知の制限: 新しい色を描く操作で変わった画素は 8 bit の表示の色から戻す（16 bit のページでも）。塗りつぶしの境目は 8 bit の操作と同じく 72 dpi で調べる。フィルターと補正は下の「フィルターと補正」。
- **フィルターと補正**（工程の群C。利用者の決定 2026-10-14: 補正は画面の色に掛ける、フィルターはインキの版ごと）:
  - 補正（レベル・トーンカーブ・色相/彩度・反転・ポスタリゼーション・2階調化・グラデーションマップ・明るさ/コントラスト・露出。補正レイヤーと `filter_raster` の両方）は、インキが規則で意味する RGB に RGB のページと同じ式（高精度の補正の連続な式）を掛け、ページの規則でインキに戻す（`render/ink` の `meaning_of`・`inks_by_rules`・`correct`）。意味する RGB: K だけ（Lab は a = b = 0）の画素は灰色（K 100% は Genko の墨 0、インキなしは白）、色の表のインキはその RGB、ほかは表示の sRGB。戻し方: 8 bit の値ちょうどの色の表の色 → 墨・白 → 灰色は K だけ（Lab は L）→ プロファイル。補正が色を変えなかった画素（往復の丸め 1e-9 以内）はインキのまま（16 bit も）。補正レイヤーの不透明度・マスク・クリップは高精度の合成と同じ形で、インキの値で混ぜる。描画モードのある補正レイヤーと、形を動かすフィルター・plugin の補正レイヤー（古い原稿）は高精度のページと同じく省いて記録（`ink_adjust_blend:…`・`adjust:…`。書き出しは `not_yet_ported`）。
  - フィルター（`filter_raster` のぼかし・シャープ・モザイク・移動ぼかし・放射ぼかし・ズームぼかし・波形・渦巻き・ゴミ取り・光彩拡散・ノイズ・線画抽出・雨）はインキの版ごとに、層の精度のまま掛ける（`render/ink_filters`）。動かす・ぼかす処理は α を掛けた値で（何も無い所に向かってぼけた線はインキのまま薄くなる）。明るさを変える処理はインキの形で: 暗くするのは K を足す（Lab は L を下げる）、明るくするのはインキを減らす（Lab は L を上げる）、コントラストは各版の平均のまわり（Lab の a・b は無彩色のまわり）、光彩は明るい画素（意味する色の明るさ。何も無い所は 8 bit の透明の画素と同じく暗い）の明るさを足す。モザイクは見本の画素の色（透明の見本は 8 bit と同じく黒）と元の α。新しく置く色（ノイズの粒・雨の筋・線画抽出の線・ゴミ取りの白と墨）はページの規則で（灰色は K だけ）。K だけの線はどのフィルターでも K だけのまま。大きさは高精度と同じく 200 dpi の画素を層の解像度に合わせる。範囲（`area`）はその中だけ。ペンの線・絵の層は先にページの規則でインキに描いてから掛け（8 bit の焼き込みと同じ。透明保護の層は自分の画素の中だけ）、掛けた層はペイントレイヤーになる。plugin のフィルターは 8 bit の絵を扱う外部の処理なので、群B の「表示の絵を貸す」方式で掛ける。
  - 画面: レベル補正・トーンカーブの窓のヒストグラムは、インキの層では意味する色の明るさで数える。
- **レイヤースタイル**（工程の群D）: インキのペイントレイヤーの効果は 8 bit の層と同じ形（効果の届く分だけ広く描いて切る）でインキに掛ける。水彩の縁は縁の α だけ Genko の墨へ寄せ（層の α はそのまま）、フチはその色の規則のインキを下に敷く（形は 8 bit の絵の α から）。表示の色（`color`）は画面ではその色の規則のインキ（α はそのまま。印刷では `color_prints` のときだけ）。トーン化（`screen`）は網点にするときだけ、インキが意味する灰色を 8 bit で網点にして規則で（K）。
- **取り込み**: CMYK のページへ RGB の絵はプロファイルで、CMYK の絵（PSD・JPEG）は絵のプロファイルからページのプロファイルへ（K を保つ。絵にプロファイルが無ければページのプロファイルとみなす）、Lab の PSD は Lab から変換して GKIR に。Lab のページへは Lab へ変換。RGB のページへの Lab の PSD は Pillow と同じ変換（Little CMS の Lab → sRGB）で読む（今までの断りを外す）。
- **画面**: 「ページ → 色モード…」（モード・精度・ICC の選択・意図・灰色の扱い・対象のページ）、ステータスにページの色モード。色の窓にペンの色のインキ（CMYK は %、Lab は L・a・b）と色域外の印（プロファイルを往復して CIE ΔE 1976 が 3 を超える色。色の表の色と灰色は出さない）。インキの値を選ぶと、その表示の RGB（規則がそのインキを当てる灰色・墨・白があればその色。無ければ表示の色を、Genko の墨と白、表で別のインキの色から 1〜数段ずらす）をペンの色にし、ページの規則がその RGB に別のインキを当てるときは、同じ色空間・同じプロファイルのページすべての色の表に組を入れる（`set_inks`、一つの取り消しで戻る）。スポイトはその点のインキ（見えている色はページを描いた値、描く先のレイヤーはその画素の値）を同じように選ぶ。値の欄は値を変えたときだけ選び直す（欄から出ただけでは何もしない）。

### COLOR-03 色モデル: RGB のプロファイル・グレー・32 bit（C++ 版。PhotoCraft の取り込み PC1a。利用者の決定 2026-10-16）

COLOR-01 の色管理と高精度。COLOR-02 の色モードを広げ、ページごとに RGB のプロファイルと精度（8・16・32 bit）、グレースケール、CMYK・Lab の 32 bit を持つ。形式は schema-v4.md の「色モデル（color-model@1）」。色モデルの無いページ（RGB・8 bit・sRGB）は今までどおり（Python 版と同じバイト・画素）。上流 PhotoCraft の色モード・深度・プロファイルの指定と変換（`image.mode.*`・`edit.assignProfile`・`edit.convertToProfile`）と問い合わせ（`document.inspect`・`document.pixel`）にあたる。上流の「文書」は Genko のページ。

- **内蔵のプロファイル**（PhotoCraft と同じ id。`native/src/core/data/profiles`、CC0。帰属は `native/third_party/photocraft/NOTICE.md`）: RGB の `srgb`（プロファイル無しと同じ）・`display-p3`・`adobe-rgb-compat`・`prophoto-compat`・`linear-srgb`・`rec2020`、グレーの `gray-gamma-2.2`・`sgray`、CMYK の `coated-cmyk`、Lab の `lab-d50`。別名（`p3`・`adobergb`・`prophoto`・`gray` など。大文字小文字・空白・記号は無視）と説明の文でも指せる。ほかに本が持つプロファイル（`"sha256:…"`）と ICC ファイル（`icc`: base64。16 MiB まで）。プロファイルは原稿に素材として埋め込む（内蔵のものも）。
- **モードと精度**（op `set_color_mode` を広げる。C++ 版だけの op）: `{"op": "set_color_mode", "page": int?（無ければ全ページと本の既定）, "mode": "rgb"|"gray"|"cmyk"|"lab", "depth": 8|16|32?（既定 8）, "profile": 内蔵の id・別名・"sha256:…"?, "icc": "<base64>"?, "intent": "perceptual"|"relative"|"saturation"|"absolute"?（既定 relative）, "bpc": bool?（黒点補正。既定 true）, "gray": "profile"|"k"?（既定 profile）, "dither": bool?, "clip_hdr": bool?, "default": bool?}`。
  - RGB: プロファイル（既定 sRGB）と精度。画素レイヤーは 8 bit なら PNG、16 なら高精度の u16、32 なら f32（HDR を保つ）。sRGB・8 bit・意図 relative・黒点補正ありなら色モデルの無いページに戻る（`color` を書かない）。
  - グレー: プロファイル（既定 `sgray`）。画素レイヤーは明るさ（0 が黒）1 版とアルファの GKIR。RGB からはプロファイル（意図・黒点補正）で変換する。ただしちょうど灰色（r = g = b）の画素は、ページが sGray か `gray: "k"` なら明るさ v/255 のまま（sGray の灰色 v は sRGB の (v, v, v) と同じ色。グレーから CMYK へ `gray: "k"` なら K だけ）。
  - CMYK・Lab: COLOR-02 のまま、32 bit（浮動小数）を加える。CMYK にはプロファイルが要る（内蔵の `coated-cmyk`、本のもの、ファイル）。Lab にはプロファイルを付けない。
  - 同じモード・同じプロファイルで精度だけを変えるときは値を写す: 8 → 16 は v × 257、8 → 32 は v / 255（バイト一致）、16 → 8 は四捨五入（`dither: true` なら決まった模様のディザ。RGB の 8 bit へ下げるとき）、32 → 8・16 は 0..1 の値を量子化。違うプロファイル・モードへは Little CMS（意図・黒点補正）。透明度とマスクはそのまま。
  - HDR（32 bit の RGB・グレーの、0..1 の外の値）を残せない変換（8・16 bit へ、ほかのモード・プロファイルへ）は断る。`clip_hdr: true` なら 0..1 に切って変換する。COLOR-02 の変換も同じ（高精度の f32 の層の HDR を黙って切らない）。
  - 断り（何も変えない）: ほかの色空間のプロファイル、Lab にプロファイル、CMYK にプロファイルが無い、読めない ICC、本の高精度の画素が 1 GiB を超える、16・32 bit の RGB のページで高精度の画素を持てない層（トーンの層、線を持つ層、フォルダーの中など。`not_yet_ported`）、マルチチャンネル（PC1d まで `not_yet_ported`）。
- **プロファイルの指定**（op `assign_profile`）: `{"op": "assign_profile", "page": int?, "profile": … | "none", "icc"?}`。画素のバイトは変えず、ページのプロファイルだけを替える（見え方が変わる）。ページの色空間のプロファイルだけ（RGB・グレー・CMYK）。`"none"` は RGB で sRGB、グレーで sGray（CMYK には断る）。Lab のページは断る。全ページを指すと、その色空間のページと本の既定だけ（一つも無ければ断る）。
- **プロファイルに変換**（op `convert_profile`）: `{"op": "convert_profile", "page": int?, "profile"|"icc", "intent"?, "bpc"?, "dither"?, "clip_hdr"?}`。見た目を保って、プロファイルの色空間へ変換する（モードはプロファイルの空間に、精度はページのまま）。
- Undo・Redo・保存・履歴は他の op と同じ。全ページへの `set_color_mode`・`assign_profile`・`convert_profile` は、ほかの人が押さえているページを一つずつ確かめる（`set_paper` と同じ）。
- **合成と表示**: プロファイル付きの RGB のページは、そのプロファイルの直線の光（トーンカーブを外した値）で合成する（`RgbSpace`）。画素レイヤーの画素はページの値。8 bit で描く要素（線・塗り・文字・フキダシ・枠など）の sRGB の色は、ページの意図・黒点補正でページの空間へ変換してから合成する（sRGB のちょうどの白と黒はページの白と黒）。画面へは相対的な色域を維持・黒点補正で sRGB にする。グレーのページは明るさで合成し、要素の色は規則（ページの色の表 → 墨は黒・白は白 → 灰色はその明るさ（sGray の値） → ほかはプロファイル）で当てる。sRGB のページの合成は前と同じバイト。
- **予算**: 本の高精度の画素（GKCR）は合わせて 1 GiB まで（利用者の決定 2026-10-16。B4・600 dpi の f32 が入る）。素材 1 つの読み込みの上限 256 MiB と、メモリー・ディスクの確かめ・PERF-G はそのまま。
- **問い合わせ**: `inspect`（snapshot）は色モデルを持つページにだけ、ページの `color`（原稿の JSON と、プロファイルの説明 `profile_description`）と層の精度（`precision`: `8`・`u16`・`f32`、GKIR はその精度）を加える（ほかの本の出力は変わらない）。`genko inspect <本> --pixel <ページ>:<x_mm>,<y_mm> [--layer ID] [--dpi N]`（C++ 版だけ。既定の dpi は原稿の dpi）: その点のページの値 `values`（RGB はプロファイルの 0..1、グレー・CMYK・Lab はインキ）、標本 `stored`（8・16 bit は整数、32 bit は float）、`alpha`、`srgb`。`--layer` はその層の画素。高精度の RGB のページの値は、層の値に、層の上に 8 bit で描いたもの（枠・台詞・効果線・ノンブル）の色をページの空間にして入れたもの。
- **書き出し**（形式に書けないものは `notes` で知らせる）:
  - PSD: グレーは Grayscale（色モード 1、8・16・32 bit）、色モデルのある RGB は RGB（色モード 3、8・16・32 bit）。ページのプロファイルを画像リソース 1039 に（sRGB のページは sRGB のもの）。CMYK・Lab の 32 bit は 16 bit で書く（Photoshop に 32 bit の CMYK・Lab は無い）。層もその精度で、RGB の層の sRGB で描いたものはページの空間へ変換する。32 bit はページの値の浮動小数（上流と同じ）。
  - TIFF: グレーのページは色が「自動」か「グレー」なら MinIsBlack（8・16・32 bit。32 は浮動小数 SampleFormat 3）とプロファイル。色モデルのある RGB のページは色が「自動」か「RGB」ならその値（8・16・32 bit）とプロファイル。CMYK・Lab の 32 bit は 16 bit。
  - PDF: グレーのページは ICCBased（N 1）、RGB のページはそのプロファイルの ICCBased（N 3）。精度は 8・16 bpc（32 bit は 16）。
  - PNG・WebToon・SNS・EPUB・Kindle・strip・layers・アニメーションなど: 表示の sRGB。
  - `notes`: 画面の色から書いたページが CMYK・Lab だけなら COLOR-02 の言葉、グレーや RGB の色モデルを含むなら「色モード・プロファイルを持つページ N ページは、この形式・色ではその値のまま書けないため、画面の色（sRGB）から変換して書き出しました」（入稿セットは PNG のこと）。32 bit を 16 bit にしたときは「32 bit のページ N ページは、この形式では 16 bit にして書き出しました」。CLI（JSON の `notes`、ふつうの出力では標準エラー）・MCP の `export`・HTTP の `/v1/export`・正式な書き出しが同じものを返す。
- **画面**: ページ → 色モード（RGB・グレースケール・CMYK・Lab と 8・16・32 bit/チャンネル。前のページに合わせて印が付く。モードはページの精度のまま、精度はモードとプロファイルのまま変える。CMYK へは内蔵の `coated-cmyk`）、ページの色モード…（対象・モード・精度・プロファイル（内蔵・原稿の・ファイル）・意図・黒点の補正・灰色の扱い・8 bit のディザ・HDR を切る。既定のものは op に書かない）。編集 → プロファイルの指定…（ページの空間のプロファイルとなし）・プロファイルに変換…（どの空間のプロファイルでも。意図・黒点の補正・ディザ・HDR）。ステータスにページのモード・精度・プロファイルの説明（例「グレー 16 bit・sGray (sRGB tone curve, Photocraft)」）。色の窓はグレーのページで K（%）の欄 1 つ。
- **既知の制限**（PC1a）: 16・32 bit の RGB のページに新しく置く 8 bit の画素（`put_raster` の PNG など）はその精度に広げない（ページの精度の層は `set_color_mode`・`convert_profile` で変換したもの）。プロファイル付きの RGB のページの層の縮小図・層の絵（`layer_image`）はページの値をそのまま表示する。`assign_profile` は要素の色を焼き込まない（要素は描くたびにページの空間へ変換する）。PSD の 16・32 bit の層の値は 8 bit の層の絵から（統合画像はページの値）、層の情報はレイヤーの節に書く（COLOR-02 の 16 bit と同じ。`Lr16`・`Lr32` は使わない）。Photoshop は 32 bit をリニアの値として読む。書き出しの統合画像と `--pixel` の値で、層の上に 8 bit で描いたものは 8 bit の色をページの空間にしたもの。

### COMP-04 既存Pythonプラグイン

既存`plugins.py`の`NAME/PARAMS/run(PIL画像)`契約を黙って廃止しない。ネイティブの拡張APIはC++本体と別プロセスの画像フィルターRPCとする。旧Pythonプラグインには同じRPCで接続する任意の外部互換ランナーを提供する。

Pythonは利用者が旧プラグインを有効にした場合だけ必要。本体・組込みフィルター・標準配布の必須依存にはしない。既定無効、利用者が選んだプラグインだけ実行し、依存がなければ日本語で理由を表示する。別プロセスはクラッシュ隔離であって安全なOSサンドボックスではないことを明示する。未保存原稿・認証情報を勝手に渡さない。

一覧表示のためにPythonファイルをimportしない。同意前はファイル名と非実行manifestだけを列挙する。明示選択・同意後に限り、そのプラグインのNAME/PARAMS取得を外部ランナーで行う。metadata取得にも時間・出力量の上限とクラッシュ処理を適用し、未選択ファイルのトップレベルコードを実行しない。

ネイティブの拡張（C++ 版だけ。2026-10-11 の利用者の判断で公開契約に加える。形式・RPC・断りは `docs/PLUGIN_NATIVE.md`）: 設定フォルダーの `plugins/<キー>/plugin.json`（プロトコル 1: `{"protocol": 1, "name": 文字, "executable": フォルダーの中の相対パス, "args"?: 文字のリスト, "params"?: PARAMS と同じ形}`）と、そのフォルダーの中のプログラムを、Python なしで画像フィルター `plugin:<キー>` にする。RPC は M3③の別プロセスの画像フィルター RPC と同じ（標準入力に 1 行の JSON `{"protocol": 1, "width", "height", "params"}` と RGBA の画素、標準出力に 1 行の JSON `{"ok": true, "width", "height"}` と同じ大きさの RGBA の画素、断りは `{"ok": false, "error"}`）。旧 Python プラグインと同じ規則に従う: 既定無効。一覧・名前・設定は plugin.json とプログラムのバイトを読むだけで何も起動しない。明示選択・同意（問いに動かすプログラムと引数を示す）の後だけ起動し、同意は plugin.json とプログラムの中身（sha256）に結び付け、変わったら選び直し。起動のたびに plugin.json とプログラムを読み直して選んだときと照らし、照らしたのと同じバイトを設定のフォルダーの中の本人だけが入れる一時フォルダー（`plugin-runs/run-…`。システムの一時フォルダーは noexec のことがあるので使わない）へ書き出して実行権を付け、その写しをシェルを通さず plugin.json の `args` だけで起動する（作業フォルダーもそこ。終わったら消す）。環境変数は旧ランナーと同じ短い一覧と `GENKO_PLUGIN_PROTOCOL=1`・`GENKO_PLUGIN_HOME`（元のプラグインのフォルダー）だけ。ハッシュが覆うのは plugin.json と本体だけで、同じフォルダーのほかのファイルは覆わない。写しを動かすので、本体の隣のライブラリは `$ORIGIN` などでは見つからない（`GENKO_PLUGIN_HOME` から探す）。時間（800 万画素ごとに 120 秒）と書き戻す量（画素のバイト数＋64 KB）の上限、落ちた・遅い・あふれた・起動できない・違う大きさの絵は日本語で知らせる。止めるとき、POSIX ではプラグインが始めたプロセスもまとめて止める（プロセスグループ。Windows ではプラグインのプロセスだけ）。標準エラーは最後の 64 KB を持つ。別プロセスはクラッシュ隔離であって安全な OS サンドボックスではない。同じキーの `<キー>.py` があるときは Python のプラグインを使う。

## 6. 追加する制作改善

### BRUSH-01 紙質画像

PNG/JPEG等を紙質として取り込み、原稿内素材として保持する。紙質の濃度、倍率、回転、反転、合成方式、適用座標を設定できる。ペン先画像と紙質は別項目。既定は紙面固定で、表示ズームにより紙質の物理サイズを変えない。

筆圧・不透明度との合成順序、乱数seed、継ぎ目方式を固定する。保存・再起動・別PC・Undo/Redo・印刷出力でも同じ線を再現する。紙質なしの既存ブラシは従来の意味を維持する。巨大画像・壊れた画像・アルファの扱いを検査する。

実装で確定した方式（M3）: 原稿の形式・合成順序・座標・seed（SplitMix64）・継ぎ目（繰り返し／折り返し）・画像の取り込み（白に重ねてグレー、縦横4096画素・64 MiBまで）・自分のブラシのライブラリ（Python版と共有する`brushes.json`には書かず`brush_papers.json`へ）は`schema-v4.md`「紙質（paper-texture@1）」と`native/src/render/paper.hpp`。解析可能な期待値fixtureと原寸基準画像は`native/tests/data/paper/`（`tools/migration/paper_reference.py`が独立に計算した期待値）。適用座標「線ごと」は線の id と最初の点から測るため、消しゴムで切った線は切れた所から紙目が新しく始まる（紙目を保つのは既定の紙面固定。線ごとの起点を切れた線へ持ち越すには線の形式の追加が要るため、M3 では行わない）。

### TEXT-01 ルビの詳細組版

- ルビ書体、本文に対するサイズ比、先頭/中央/末尾揃え、本文との距離、ルビ字間を編集できる。
- 絶対距離はmm、文字倍率は無次元で保存する。既定値未指定の旧原稿は現行の配置解釈を維持する。
- 親文字とルビの対応範囲を位置情報で保持し、同じ語が複数ある文章を誤指定しない。互換の`ruby_runs`入力は明示ルールで新しい範囲情報に変換する。
- 範囲はUnicode拡張書記素クラスタを単位とする半開区間[start,end)。採用Unicode版を固定し、UTF-16コード単位と混同しない。前方挿入は両端を移動、範囲直前への挿入は親文字へ含めず、範囲末尾への挿入も含めない。後方編集では対応を変えない。
- 親文字内部への挿入、部分削除、範囲をまたぐ置換、改行挿入は、機械的に読みを推測せず、そのルビを要確認にする。元の親文字・読みを保全して再割当/解除を選ばせる。親文字全削除ではルビを描画せず、Undoで本文とともに戻る履歴へ保持する。要確認のまま正式出力は停止する。全文置換にも同じ規則を適用し、IME未確定文字では確定データを変更しない。
- 禁則による行送りだけでは対応範囲を変更しない。重なり・はみ出しは警告し、無断で縮小・削除しない。
- 日本語IMEの変換中と確定後、Undo、全文検索置換、縦横切替、保存再開、PDF/PNGを試験する。

### PSD-01 編集可能な文字の受け渡し

PSD出力に「文字を編集可能なレイヤーとして保持」と「見た目優先で画像化」を明確に分ける。編集可能モードでは本文、縦横方向、フォント・サイズ・位置・色・必要な変形をPSD文字構造へ書き、画像層に見えるだけの台詞を文字レイヤー成功と数えない。

- 必須対応は縦横本文、改行、複数の部分書式run（フォント・サイズ・太字/斜体・色）、字間、段落揃え、平行移動・回転・拡縮、単色の縁取りと塗りを持つ効果文字。本文・ルビの文字列を編集可能に保つ。これらを未対応扱いして出力拒否/画像化した場合は未完成とする。
- 画像/グラデーションによる文字塗り、任意パス文字、非線形ワープ、特殊な多重縁などは、初版のPSD編集可能モードでは明示的に未対応としてよい。本体・PNG/PDF等の継承機能からは削らない。対応表を配布物に含める。
- 本文とルビは別の編集可能文字レイヤーに分け、同一グループと対応IDを付ける。フキダシは別層。PSD先で本文を変更した後にルビが自動追従する保証はしない。
- PSDで表現できない装飾・ワープ等は、対象と影響を出力前に表示する。「編集可能」指定のまま黙って画像化しない。厳密モードは出力を停止し、利用者が見た目優先を選んだ場合だけ画像化する。
- フォント不足や置換は警告。許諾なしにフォントファイルをPSDや配布物へ埋め込まない。
- 受取アプリでの再編集は利用者判断でwaived。ACCEPTANCE.md §6に従い、PSD文字構造とKrita読込を代替検査し、Photoshop/CSPでの再編集は未確認と明記する。購入・登録を行わない。

## 7. 利用者向け改善

### UX-01 導入と最初の制作

Windowsはユーザー単位インストーラーとZIP、Linuxは対象環境で動く自己完結した配布物を用意し、Python設定なしで起動する。原稿を作る→コマを割る→線・台詞を置く→保存→開き直す→出力まで、日本語で案内する。手描きだけならAI設定を要求しない。

署名証明書未取得の場合は警告と配布元確認方法を説明し、「警告なし導入」を合格にしない。OSの保護解除・管理者権限付与を前提にしない。

設定の置き場所（M6、利用者の決定 2026-10-15「分けて初回に尋ねる」）: C++ 版は自分の設定フォルダー（Linux `$XDG_CONFIG_HOME/genko-studio` または `~/.config/genko-studio`、Windows `%APPDATA%\GenkoStudio`）に、環境設定（`settings.ini`）・最近の原稿・自作のブラシ・色・ポーズ・素材・オートアクション・AI 接続の鍵・プラグインを持ち、Python 版（`~/.config/genko`・`%APPDATA%\genko` と `QSettings("Genko", "Genko Studio")`）と並べて使える。初めて起動したとき、Python 版の設定があれば「引き継ぎますか？」と尋ね、はいのときだけ写す。写さないもの: 復旧用のコピー（`recovery/`）・キャッシュ（`cache/`・`thumbs/`・`fonts.json`）・プラグインの実行跡・ロック・書きかけのファイル。C++ 版にすでにある設定やファイルの上には写さない（中身の違うものは写さなかったと知らせる）。AI 接続の鍵は持ち主だけが読めるまま写し、新しいフォルダーは旧版のフォルダーと同じ権限で作る。リンクはリンクのまま写さない: ファイルへのリンクは指す先の中身を写し、フォルダーへのリンクは写さずに知らせる（C++ 版の変更がリンクを通って旧版のファイルに及ばないように）。旧版の設定は、あるかを確かめてから開く（Windows のレジストリは、無いキーを開くと作られるため）。同時に起動した二つのアプリが重ねて聞かないよう、新しいフォルダーのロックの下で聞く。Python 版の設定は読むだけで、変えず・動かさず・消さない。答えは一度だけ聞く（`migration/done`: copied・declined・none）。写せないものがあれば知らせ、次の起動でもう一度聞く（写せたものはそのまま）。`$GENKO_CONFIG_DIR` は従来どおりそのフォルダーを使い、引き継ぎは尋ねない（試験 `test_migration`）。引き継ぐかをまだ聞いていない間は、コマンドライン（`genko` のアプリ以外のコマンド、MCP を含む）が標準エラーにそのことを書く（AI 接続の鍵が見つからない理由が分かるように）。MCP の `inspect` の説明文は Python と同じ文のまま（プラグインの置き場所の例が旧版の場所。実際の場所は `inspect` の `plugins` が返す `folder`）。

### AI-01 接続の見える化

「未設定」「設定済み・未接続」「接続済み」「処理中」「人の確認待ち」「失敗」を区別する。設定コピー、対象クライアントの説明、テスト接続、原稿・会話の対応、最後の呼出しとエラー原因を画面から確認できる。

プロセスが起動しただけで「AIに依頼できた」と表示しない。接続テストは原稿を変更しない要求で行い、AI生成や課金を勝手に実行しない。外部クライアント設定の書換えは変更内容表示・バックアップ・利用者確認付き。トークン等を画面・ログ・配布証拠へ露出させない。

実装（M5④）: AI と作る の状態の一語と事実、テスト接続（`initialize`・`tools/list` だけ）、Claude Desktop と Hermes Agent の設定ファイルの変更案・写し・確認・取りやめ・元に戻す、原稿と会話の選択。Python との違いは COMP-01a の M5 の行。テスト接続が「接続済み」と言うのは Genko のサーバーが応答したことだけで、AI のアプリからつながったかは、AI が道具を使った記録（最後の呼び出し）で示す。設定ファイルへの書き込みは、安全に解けない形では書かずに理由を出す: Hermes の YAML で、一番上や mcp_servers・genko の中に鍵として読めない行（流れ形式の `{` `[`、明示の鍵 `?`、アンカー `&`・別名 `*`・タグ `!`、ブロックの `|` `>`、指示 `%`、`<<` の取り込み）があるとき、文書の区切りが二つ以上あるとき（先頭の `---` 一つだけは受け付けて残す）。Claude Desktop の JSON で、NaN・Infinity・1e400 のような数、64 ビットを超える整数、同じオブジェクトに同じ鍵が二つあるとき、UTF-8 でない（UTF-16 などは BOM から言う）とき。UTF-8 の BOM は読み飛ばして書き戻す。genko の項目を書き換えても、その後ろのコメントと空行は残す。「元に戻す」が今のファイルを残す写しは `.genko-before-undo-<時刻>` で、Genko の写し（`.genko-backup-<時刻>`）と分けるので、2 回押しても戻し直さない（今のファイルが写しと同じなら押せない）。Windows の Claude Desktop の設定ファイルは、Microsoft Store（MSIX）版の場所（`%LOCALAPPDATA%\Packages\Claude_*\LocalCache\Roaming\Claude\claude_desktop_config.json`）にフォルダーがあればそちらを先に見て、なければ `%APPDATA%\Claude\` を見る（既知の制限: Windows の実機では M6 で確かめる。パッケージ名の後ろの部分は決め打ちしない）。テスト接続は、原稿のフォルダーが無ければ何も起動せず、フォルダーも作らずに理由を出す。既知の制限（M6 の範囲）: Windows で genko:// のリンクを開くたびにコンソールの窓が一瞬出る（`genko app` を受け渡し役として起動するため）。AppImage で動かした Genko の「サイトのボタンで開けるようにする」は、一時的にマウントされた場所（`/tmp/.mount_*`）を登録してしまう（`$APPIMAGE` の場所を使うかを M6 で決める）。初めての設定から結果までの流れ（設定を書く → テスト接続 → 依頼 → 承認・返事 → AI が読み戻す）は、試験の代わりのサーバーと、この build の `genko mcp`（M5③。initialize は 2025-06-18。道具の記録 `studio/logs/tools.jsonl` と `studio/presence.json` を Python の genko/mcp/server.py と同じ形で書き、Python の読み手が同じに読む）の両方で通す。

## 8. APIと安全境界

### API-01 共通契約

GUI/CLI/HTTP/MCPは同じ権限判定・原稿モデルを使う。操作名、引数、dry-run、成功/失敗、画像応答、ジョブ状態、session、エラーコードを台帳化する。ヘッドレス動作にQWidgetやディスプレイ接続を要求しない。MCPのプロトコル版・能力交渉・取消・stderrログ・stdout汚染防止を実クライアントで確認する。

MCP道具数と編集op数は別物。MCPに公開しない人間専用opを、移植時に一括公開しない。文頭の古いコメントではなく現行の`record_chat_approval`を含む実装・ゲートを引き継ぐ。

### API-02 権限と入力防御

actorの`human:`/`ai:`、固定欄、ページロック、承認、session間の干渉防止、他者変更のUndo拒否を維持する。チャット承認は本人の明示意思と原稿側の許可があるときだけ記録でき、停止設定をAIが解除できない。

HTTPは既定でループバック、`/health`以外の認証、Host/Origin検査、root以下へのパス制限を維持する。要求内の素材・フォント・ZIP・シンボリックリンク・URL・外部コマンドにも検証を適用する。HTTP本文上限の現行64MiBを維持し、展開後寸法・圧縮爆弾・深いJSONにも別の上限を設ける。許可されないパスを正規化だけで承認しない。

生成AIクライアントやアップスケーラーの認証方式、課金先、許可コマンドを変更しない。原稿・ログを外部へ自動送信しない。
