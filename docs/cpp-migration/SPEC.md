# Genko Studio C++移行・改善仕様

版: 1.1 / 作成日: 2026-10-01 / 更新日: 2026-10-04 / 状態: 承認済み計画に沿って移行中

## 1. 決定事項と適用範囲

- **採用構成はC++20＋Qt 6。比較用のPython改良版、捨てる試作、言語選定のA/B開発は作らない。** 各工程で書くコードは最終製品の一部とする。
- 目標はGUI、描画、編集、保存、書き出し、CLI、HTTP、MCPをC++へ移行した製品。Python製本体を内部呼び出しして動くものを完成版としない。
- 移行と同時に、本書の保存保護・性能・導入・写植・PSD文字・紙質・画面・AI接続の改善を実装する。CSP全機能の複製や売上保証を目標にはしない。
- 既存のPython版は利用中の安定版・移行元として保持する。新機能を二重実装せず、C++版だけを開発する。既存ファイルの契約確認・入出力互換試験は、禁止する「別案を開発して性能を比較すること」には当たらない。
- 当初の計画作成後、利用者の指示で実装・検証を開始した。2026-10-04の整理指示により検証頻度をVALIDATION.mdへ一本化する。既存版の置換、本番原稿の使用、新費用、権限変更は別の承認境界を維持する。

## 2. 現行基準と仕様の優先順位

基準コミット: `1b7b1d7030d4188d7ebd5e398d010b3ed98b220f`。

現行READMEの正式対象はWindowsとLinux。手描き、コマ、写植、レイヤー、トーン、素材、3D、アニメーション、各形式の入出力、外部AIとの制作工程を引き継ぐ。古い設計文書にない機能も、現行実装に存在するものは移行対象に含める。

静的棚卸しは`baseline-inventory.json`を正本とする。操作スキーマ168種、MCP道具41種、MCPリソース4種、Pythonモジュール146本、試験ファイル118本、テスト関数定義880個を抽出した。これは実行ケース数でも合格数でもない。以前の954ケース中952成功・性能2件未達、選択試験33件成功とは区別する。

優先順位は、今回の明示指示→本仕様と受入基準→固定した現行データ・公開インターフェースの契約→現行の設計メモ。`CSP_GAP.md`等の「対応済み」記述だけで実動作の合格を扱わない。既知の不具合まで互換動作として再現しない。

## 3. 製品構成

### ARCH-01 本体と言語

- C++20、Qt 6 Widgetsを使用。CMake＋Ninja、CTest＋Qt Testを標準構成とする。Qtの採用パッチ版、コンパイラ、依存版・取得元・ハッシュをM0で固定する。最新という理由だけで開発途中に更新しない。
- Windows 11 x64、Ubuntu 24.04 x86_64を最初の正式対象とする。OS別検証と実機代替の範囲はACCEPTANCE.md §6に従う。macOS・ARM・モバイルは本移行の正式対応範囲外であり、非対応化の断定ではない。
- 配布物はPython、uv、pip、開発用コンパイラを利用者に要求しない。テスト・文書生成のPythonは開発環境だけで使用可。
- 外部AIクライアント、利用者登録のアップスケーラー、既存Pythonプラグインは外部拡張として区別する。Pythonプラグイン互換の条件はCOMP-04に従い、本体のPython残置の口実にしない。

### ARCH-02 モジュールと依存方向

`native/`以下に次の最終製品モジュールを置く（ここでは配置の仕様だけを定義する）。

- `core/`: Document、Page、Frame、Layer、Stroke、Text、ID、単位、CommandBus、権限、変更集合。GUIに依存しない。
- `storage/`: 旧形式読込、v4保存、素材ストア、排他、トランザクション、履歴、復旧。
- `render/`: 描線、タイル、レイヤー合成、トーン、効果、3D、色管理。画面と出力で同じ内容モデルを使う。
- `text/`: 縦書き、字体処理、禁則、ルビ、字間、フキダシ、グリフ配置。
- `formats/`: PSD/PSB読込、PSD出力、PNG/TIFF/PDF/EPUB等の出力。外部入力を検証してcoreへ渡す。
- `studio/`: 企画・脚本・依頼・候補・承認・相談・共同編集・制作順序。
- `api/`: CLI、HTTP、MCP、設定変換、エラー整形。core/studioの同じコマンドを呼ぶ。
- `app/`: Qt画面、IME、ペン、ショートカット、案内、アクセシビリティ。
- `tests/`、`packaging/`: 契約・受入試験、配布。`genko`一つのCLIから`app`、`mcp`、`serve`等を起動できる構成とする。

appやAPIからJSONを直接書き換える経路は禁止。変更はCommandBus→検証・権限判定→変更集合→保存サービスへ集約する。描画途中の一時線は可逆なプレビューとし、線の確定時にコマンド化する。

### ARCH-03 スレッド・所有権

- QWidget/QPixmap等のGUI操作はメインスレッドだけ。ワーカーは独立した画像バッファと不変スナップショットを扱い、結果をキューで返す。
- 原稿変更は一つの実行列で順序付ける。文書リビジョンと描画世代IDを持ち、古い結果は画面へ適用しない。ワーカーから生ポインタで編集モデルを変更しない。
- 保存・出力・重いフィルター・細部レンダリングはGUIスレッドを占有しない。入力受付、進捗、取消を継続する。単にスレッドに移しただけで完了扱いにしない。
- RAII、所有権が明確なスマートポインタ、境界チェックを基本とする。画像寸法・演算のオーバーフロー、use-after-free、データ競合を検査する。

### ARCH-04 描画と依存ライブラリ

- CPUタイル描画を必須経路とし、専用GPUを起動条件にしない。表示合成でQtのGPU機能を使っても、CPU代替経路と同じ原稿結果を保証する。
- FreeType＋HarfBuzzを文字の字体処理候補ではなく採用構成とし、縦書き・ルビ配置はGenkoのC++レイアウト層で扱う。QTextEditだけで原稿組版を代替しない。
- 色変換はLittle CMS、画像形式はQtの利用可能なコーデックとlibpng/libjpeg-turbo/libtiff/libwebp、圧縮はzlibを用途別に使用。JSONは64bit整数を保てるライブラリを使用し、QJsonの数値変換でID・リビジョンを丸めない。
- 既存PSDの読書き仕様はC++へ移し、PSDの文字拡張を追加する。Pythonのpsd-toolsを製品実行時の変換器にしない。
- 動画出力に外部FFmpegを使う場合はライセンスと対応codecを明記する。自動ダウンロード、有料codec契約は行わない。現行機能の外部依存を黙って削除しない。

### ARCH-05 費用・ライセンス

QtはLGPL利用条件を満たす動的リンク構成を基本とする。MITの本体と第三者ライセンスは別管理。ライセンス文、対応ソースの提供義務、ライブラリ差替え・再リンク条件、変更箇所を確認し、GPL専用モジュールを無断追加しない。依存物・フォント・アイコンのSBOMを配布する。商用Qt、署名証明書、新クラウド、新API課金が必要ならその項目だけ停止して承認を求める。

## 4. 原稿・互換性・保存

### DATA-01 旧原稿を壊さない移行

- `.genko`は拡張子付きディレクトリであり、単一ZIPと誤認しない。旧v1/v2/v3を読めるC++リーダーを用意する。
- 初回は旧writerとGCを停止し、既存writerと協調する排他の下で全体の固定コピーを取得する。原本が使用中、協調排他を確保できない、収集途中の変更を検出した場合は公開せず停止する。固定コピーのmanifest・履歴・監査・履歴から到達する素材までハッシュを固定してから変換する。原本の内容・設定・承認記録は書き換えない。既存ロックファイルの排他取得と内容変更を区別する。
- 固定コピーを読み取り専用で解析し、欠損素材・未知機能・不足フォントを一覧化。利用者が選んだ別の`.genko`へ変換する。稼働中の原稿ディレクトリを直接走査した結果だけで移行成功としない。
- C++版の書込み形式はv4。`version:4`、読取最低版、writer情報、拡張機能識別子を持つ。旧版が新原稿を書き戻して情報を落とすことを避ける。v4をPython版で編集する運用は提供しない。
- 旧ID、mm単位、ページ順、コマ木、本文、改行、ルビ、レイヤー順、素材、筆圧、承認・actor・sessionを維持する。旧履歴は不変の保全領域へ原本バイトとハッシュ参照ごと保存する。旧スナップショットのハッシュ→変換済みv4状態IDの対応表と移行境界を作り、v2の相対参照を含む履歴から到達する素材も取り込む。
- 旧履歴へのUndo/Redoは対応表から内容を取り出し、権限を再検証した**新しいv4 transaction**として確定する。旧project.jsonをそのまま書き戻さず、v4→v3等への巻戻しを禁止する。変換前後の監査を連結するが、過去の承認を新規承認として作り直さない。
- 将来の未知フィールドは拡張領域へ保持。未実装の表示・編集意味を持つ場合は該当操作または原稿を読み取り専用にし、空として保存しない。

### DATA-02 素材・数値・スキーマ

- `assets/<先頭2桁>/<sha256><suffix>`と`sha256:<64桁hex>`を引き継ぐ。読込時は参照形式、パス、必要に応じ実バイトのハッシュを検証する。
- 既存の画像・スナップショットのバイト列を保存する。JSONを再整形して既存ハッシュを流用しない。新規JSONはUTF-8、固定キー順、ロケール非依存数値、LFとし、テストベクトルで仕様固定する。
- 筆跡のpacked little-endian float64とbase64を正しく読む。32bit化による座標・筆圧の精度低下、NaN/Infinityの混入、リビジョンの丸めを禁止する。
- 書式拡張は`docs/cpp-migration/schema-v4.md`へM1で確定する。必須項目、既定値、単位、範囲、未知フィールド、前後互換、JSON例を定義してから本番用writerを実装する。

### SAVE-01 保存状態と終了保護

表示状態は「保存済み」「未保存」「保存中」「保存失敗」「復旧用コピーのみ」の5種。保存失敗時は理由・保存先・最後の成功時刻を表示し、再試行、別名保存、復旧コピー作成を選べる。復旧コピーだけの成功を通常保存済みにしない。

未保存・保存失敗・保存中に閉じる、原稿切替、アプリ終了を行った場合は既定で停止する。「保存して閉じる」は保存成功後のみ終了。「保存せず破棄」は明示確認を要し、キャンセルが安全側の既定。例外が発生しても画面とメモリ内の原稿を維持する。

保存中に追加した編集は別世代としてdirtyを維持する。古い保存完了通知で新しい編集を保存済みにしない。OS強制終了・電源断で未永続化の編集を完全保証するとは表示しない。

### SAVE-02 原子的な確定と復旧

同一原稿の書込みはOS排他とbase_revision検証で直列化する。v4の公開revisionは単調増加の永続化世代であり、Undo/Redo、復旧内容の採用も新しい世代を割り当てる。復元対象のhistory_state_idと世代は別で、過去のrevisionを再利用しない。base_revisionにはこの世代を使い、編集→Undo後に旧クライアントが一致するABA競合を防ぐ。POSIXのflockとWindowsの既存互換範囲ロックを扱い、単なるQLockFile置換で既存版との排他を破らない。競合時は相手の変更を無言で上書きしない。

保存手順は次の通り。

1. 対象リビジョンの不変スナップショットを作り、変更素材と履歴用before/afterを一時ファイルへ出す。
2. 新素材をflushし、同一ボリューム内のrenameで確定する。既存ハッシュの内容を書き換えない。
3. transaction_id、before/after、base_revision、actor、必要素材を持つprepare記録を永続化する。
4. `project.json`を一時ファイル→原子的置換で確定し、履歴と承認監査をtransaction_idで重複なく記録する。
5. commit記録と必要なOS同期が成功してから、該当リビジョンを保存済みとして通知する。

起動時、保存失敗時、および次の更新・Undo・保存の前に、排他下で未完了transactionと末尾破損ログを検査し、最後の整合した確定点へ復旧する。同一transaction_idの再試行は一度だけ確定し、既に確定した場合は同じ確定世代を返す。修復できるまでは書込みを止め、画面のdirty状態とディスクの確定世代を再照合する。projectだけ更新済みならprepareから履歴を修復し、同じ承認を二重記録しない。素材不足なら旧整合点を保持して読取専用とする。復旧できないときに空原稿で上書きしない。ファイルシステムが永続化を保証しない場合は警告し、ネットワークドライブやクラウド同期先を初期の安全保証範囲に含めない。

### SAVE-03 自動保存・履歴・GC

- 入力を止めない自動保存と、別の復旧領域へのチェックポイントを設ける。既定は変更の休止後2秒、連続作業時は最大10秒で復旧点作成を開始する。実際の成功リビジョン・時刻を表示する。
- 保存失敗中は復旧点の有無を知らせ、原稿領域も復旧領域も書けなければ明示警告する。成功していない編集を保護済みと呼ばない。
- 原稿・復旧点・Undo/Redo・進行中出力・transactionが参照する素材はGCしない。GCは排他、dry-run、対象表示を備え、初期移行時には自動実行しない。
- actor/sessionごとのUndoと人間の承認変更の制約を維持する。履歴復元による承認回避を拒否する。
- 既知の制限（2026-10、M5 出口）: 画面の変更のうち本の中身を変えるもの（線・台詞・ページの操作など）が保存を待つ間に、別の書き手（AI の `apply_ops` など）がページの番号と ID の対応を変える（並べ替え・削除・挿入）と、その変更は番号のまま別のページに当てず、ID で付け直すこともせず、競合（`rebase_conflict`）として未保存のまま残す（画面のメモリーと復旧用コピーにはある）。人がその変更を元に戻すまで、後の変更も原稿に書かない。コマの選択（`select_frame`）だけは本の中身ではないので付け直す（COMP-01a）。
- 既知の制限（2026-10、M5④）: C++ 版の原稿（v4）には旧版（Python 版）の `genko gc`・`genko undo` を使わない。旧版の gc は v4 を断らず、v3 の journal が名指すものだけを残すため、1 日より古い v4 の履歴の状態・状態だけが名指す素材・変換した旧履歴を消す（旧版の undo は v4 の journal を読めずに止まる）。消された後も C++ 版は原稿を今の中身のまま開き、保存・gc・修復を続け、消えた所より前に戻る Undo（その状態へ進む Redo）は何も書かずに `history_missing` で断り、`genko doctor` が消えたものと Undo が戻れる所までを報告する（schema-v4 §8）。

## 5. 機能を落とさない移行

### COMP-01 操作・画面の網羅

168種の操作を最低限の棚卸し単位にし、名前だけでなく引数、既定値、成功結果、失敗時の無変更、Undo、保存再開、GUI入口を対応付ける。M0で実dispatchとスキーマ差分、GUI専用機能、設定、素材・ブラシ・ワークスペース、ショートカットを追記する。移行対象の省略は利用者の明示承認なしでは認めない。

#### COMP-01a 現行の不具合を再現しない変更（実装で確定したもの）

§2「既知の不具合まで互換動作として再現しない」に従い、原稿の破損・無限ループ・二重参照・安全の問題につながる現行の挙動は、C++ 版では入力を拒否する（原稿は変えない）。出力の見た目と数値の細部は現行と同じにする。

| 現行の挙動 | C++ 版 | 工程 |
|---|---|---|
| 高さ 0 のコマで読み順の計算が止まらない | そのコマ単独で行を作って終える | M1 |
| `raster_relpath`・素材参照が原稿フォルダーの外を指せる | 読まずに報告し、読取専用で開く | M1 |
| 欠けた素材・ページより下の未知キー・配置画像層の筆跡が保存で黙って消える | 報告して読取専用で開き、保存を拒否 | M1 |
| 型の合わない値・NaN/Infinity・64bit を超える整数 | 既定値か null に置き換えて報告し、読取専用。`--accept-repairs` で変換 | M1 |
| op の NaN/Infinity | 拒否 | M1 |
| journal の読込が U+2028 で行を分ける | `\n` だけで分ける | M1 |
| `reorder_layers` に同じ id が重複すると同じ層が 2 か所に入り、片方の編集が他方に出る | `ids must not repeat` で拒否 | M2 |
| `reorder_layers` の order に無い層が消える（空の order で全部消える、未知の id は無視） | `order must list every layer of the page once` で拒否 | M2 |
| 存在しないページへの `lock_page`／`unlock_page` が成功する | `no page <n>` で拒否 | M2 |
| `select_frame` がページに無い `frame_id` を受け付ける | 拒否 | M2 |
| `set_layer` の `parent` に任意の値を保存する | ページのフォルダー層の id か null だけ受け付ける | M2 |
| `for_pages` の `pages` の文字列を 1 文字ずつのページ番号として読む | `all`・`body`・整数の配列だけ受け付ける | M2 |
| 巨大な座標でメモリが尽きるまで処理が続く | 1000 万ステップで打ち切ってエラー | M2 |
| `delete_tone` がトーン以外の層も削除する | `layer <id> is not a tone layer` で拒否 | M3 |
| `pose_mannequin` が人形以外の 3D オブジェクトの寸法・姿勢を書き換える | `3D <id> is not a mannequin` で拒否（一括操作の他の変更も保存しない） | M3 |
| モデルの循環ノード・巨大な頂点数や面、トーン・効果線・定規の巨大な反復 | 共通の `core/limits.hpp` の上限で拒否 | M3 |
| トーンの勾配角度に文字列の `inf`・`nan` 等を保存し、後の描画が失敗する | 数値変換後の勾配角度も有限性を検査し、保存前に拒否 | M3 |
| 定規の点数計算で int64 の飽和値へ加算する／有限入力から非有限の輪郭ができ、ストロークとして保存される | 加算前に共通の点数上限を検査／新たに作る点の有限性を保存前に検査して拒否 | M3 |
| `lt_convert` がロック済みの出力先層に線を追加できる | `the layer is locked` で一括操作ごと拒否し、前置変更も保存しない | M3 |

### COLOR-02 CMYK・Lab のページ（C++ 版。利用者の決定 2026-10-13）

COLOR-01 の CMYK・Lab での編集。ページごとに色モード（RGB・CMYK・Lab）と精度（8・16 bit）を持ち、CMYK は ICC プロファイルを原稿に埋め込む。形式は schema-v4.md の「色モード（color-mode@1）」。CMYK・Lab のページでもページの機能を全部使える（工程の群ごとに統合する。まだ統合していない機能は `not_yet_ported` で断り、黙って RGB で描いたり変えたりしない）。RGB のページは今までどおり（Python 版と同じ画素）。

- **合成**: ページの色空間のまま合成する（RGB を通さない）。紙はインキなし（CMYK）・L 100（Lab）。不透明度・マスク・クリップは RGB のページと同じ形でインキの値に掛ける。
  - CMYK の描画モード: 各版を (1 − インキ) にして高精度の合成と同じ式で混ぜ、戻す（Photoshop の CMYK と同じ考え。乗算はインキが増える）。色相・彩度・カラー・輝度は (1 − C, 1 − M, 1 − Y) を RGB として式を当て、K は色相・彩度・カラーでは下の層の K、輝度では上の層の K。
  - Lab の描画モード: 符号化した値（L/100、(a+128)/255、(b+128)/255）の各版に式を当てる。使えるのは通常・乗算・スクリーン・オーバーレイ・加算・焼き込み（リニア）・ソフトライト・ハードライト。ほかのモードは Lab のページでは使えない（その op を断り、その層を持つページを Lab にする変換も断る）。
  - 色のページなので、モノクロの仕上げ（灰色を網点に）はしない。トーンは RGB のカラーのページと同じく網点にせずその濃さで描き、色は下の規則でインキに当てる（黒のトーンは K だけ、Lab は L）。補正レイヤーは下の「フィルターと補正」のとおり合成する。
  - 要素の色（線・塗り・文字・フキダシ・枠線・効果線・トーンなど）は RGB のまま持ち、schema-v4 の規則（ページの色の表 → 既定の墨と白 → 灰色は K だけ → プロファイルで変換）でインキに当てる。8 bit で描く要素は、黒と白の 2 枚の紙に描いて各画素の被覆と色を取り出し、その色をインキに当ててから合成する（色の表の色と灰色は正確。2 つの色の境目のアンチエイリアスの画素は変換した色）。
- **表示**: 合成したインキを sRGB にして画面・サムネイル・プレビュー・`genko render`・MCP の絵に出す（CMYK はページのプロファイルから、Lab は D50 から。相対的な色域を維持、黒点補正）。画面だけの印（下描きの色・ガイド・3D・定規・折り目・オニオンスキン）は表示の上に描く。「CMYK で見る（色校正）」（PC1b から「色の校正」。COLOR-03）は RGB と Lab のページに掛かり、CMYK のページはもともとインキの表示。
- **変換**（op `set_color_mode`。C++ 版だけの op、公開の `genko schema` は Python のまま）: `{"op": "set_color_mode", "page": int?（無ければ全ページと本の既定）, "mode": "rgb"|"cmyk"|"lab", "depth": 8|16?（既定 8）, "icc": "<ICC の base64>"? か "profile": "sha256:…"?（CMYK で必須。本が持つプロファイル）, "intent": "perceptual"|"relative"|"saturation"|"absolute"?（既定 relative）, "gray": "profile"|"k"?（既定 profile）, "default": bool?（ページを指したときも本の既定にする）}`。
  - 画素レイヤー（8 bit の PNG・高精度の画素・GKIR）を新しい色空間の GKIR に変換する（RGB へは `depth` 8（既定）なら PNG、16 なら高精度の u16。高精度の画素が持てない層の設定なら断る）。RGB → CMYK はプロファイル（意図・黒点補正）、`gray: "k"` ならちょうど灰色（r = g = b）の画素は K だけ（K = 1 − v/255。線画向け）。CMYK → CMYK（別のプロファイル）は K を保つ変換（Little CMS の preserve K only）。CMYK ↔ Lab、RGB ↔ Lab も Little CMS。透明度とマスクはそのまま。8 ↔ 16 bit は値を量子化し直す。
  - 要素の色は RGB のまま変えない（RGB に戻すと色の表は無くなり、要素は RGB の色で描かれる）。
  - Undo・Redo・保存・履歴は他の op と同じ。変換できないもの（Lab で使えない描画モードの層など）があれば何も変えずに断る。
- **色の表**（op `set_inks`）: `{"op": "set_inks", "page": int?（無ければ CMYK・Lab の全ページ）, "inks": [[[r, g, b], [v…]], …], "replace": bool?}`。RGB の色を正確なインキに当てる。画面の色の窓で CMYK・Lab の値を選ぶと、その色の表示用の RGB（変換して丸めた値。同じ RGB が別のインキに使われていれば 1 ずらす）を要素に、組を色の表に入れる。
- **書き出し**:
  - PDF・TIFF: 色が「自動」か「CMYK」なら、CMYK のページはインキの値のまま（8/16 bit）、そのページのプロファイルを埋め込む（書き出しの ICC は RGB のページの変換だけに使う）。Lab のページは「自動」で Lab のまま（PDF は `/Lab`、TIFF は CIELab）、「CMYK」では書き出しの ICC で変換。「RGB」「グレー」「白黒」は表示の sRGB から今までどおり。
  - PSD: CMYK のページは CMYK（色モード 4、8/16 bit、プロファイルを埋め込む）、Lab のページは Lab（色モード 9）で、レイヤーもインキで書く。編集可能な文字（PSD-01）も同じく書き（群D）、文字の層の画素はインキ、グループの記録はページの版の数。CMYK のページの文字の色は規則のインキ（EngineData の FillColor Type 2: α・C・M・Y・K）、縁取り（lfx2）の色は CMYC（%）。Lab のページの縁取りは LbCl、文字の色は RGB（Type 1。Lab の Type は確かめられない）。Photoshop での確認はしていない（psd-tools とこのビルドの読み手で照合）。
  - PNG・WebToon・SNS・EPUB・Kindle・strip・layers・アニメーション・印刷: 表示の sRGB。入稿セットは TIFF がインキのまま、PNG が sRGB。CMYK・Lab のページを sRGB にして書いたときは、書き出しの返事に `notes`（「CMYK・Lab のページ N ページは…画面の色（sRGB）から変換して書き出しました」）を付けて知らせる（黙って変換しない）: CLI（JSON の `notes`、ふつうの出力では標準エラー）、MCP の `export`（`notes`）、HTTP API の `/v1/export`（`notes`）、正式な書き出し、書き出しの窓とタイムラインの動画の書き出し（知らせの文）。タイムラプスは記録した履歴の絵なので対象外。
- **画素の操作**（工程の群B、`render/ink_edit`）:
  - 画素を消す・動かすだけの操作はインキの値のまま直接扱う（高精度の層と同じ）: 消しゴム（`erase`・`erase_raster`。ぼかし・ざらつきは 8 bit の消しゴムと同じ形で α を減らす。「線全体」「交点まで」は RGB のページと同じく線だけで画素は消さない）・範囲の削除（`delete_area`）・変形とワープ（`transform_area`。範囲の画素を持ち上げ、α を掛けたインキで再標本化して置く）・インキの断片の貼り付け（`paste`。画面のコピーは CMYK・Lab のページで範囲のインキを断片として持ち、同じ色モード・精度・プロファイルのページのペイントレイヤーへ、回さない貼り付けならインキのまま置く。ほかは表示の絵として貼る）・判型の変更（`set_page_spec`。古い枠から新しい枠へ 200 dpi・バイリニア）。道具が触れない画素は 16 bit の値のまま、動かした画素はそのインキのまま。
  - 結合と変換（`merge_down`・`merge_layers`・`merge_visible`・`convert_layer` のペイントへ）は、結合する層を op の前の設定のままページの合成と同じ形でインキで合成し直す（`render::composite_ink_layers`。透明から合成し、どの層も無い所は透明のまま。層の順・不透明度・描画モード・クリップ・紙は 8 bit の結合と同じ取り方）。
  - 新しい色を描く・混ぜる操作は、op の前に対象の層（ページ全体を合成する操作・層を作る操作ではそのページのインキの層すべて）を表示の絵（sRGB の 8 bit RGBA。RGB のペイントレイヤーの PNG）にして今までの操作に渡し、op の後でインキに戻す: 色混ぜ・ゆがみ（`smudge`・`liquify`）・塗りつぶし・グラデーション・図形・塗り残し（`flood_fill`・`gradient_fill`・`add_shape`・`fill_gaps`）・定規から（`ruler_to_layer`）・ライトテーブル（`lt_convert`）・3D から（`render_prims`・`trace_prims`）・高精度の画素（`put_color_raster`）。貸した層に op が絵として置いたもの（色混ぜが変えた範囲の絵など）は貸した絵に描いてから戻す。戻し方: op が色を変えなかった画素（同じ場所で 1 チャンネル 2 以内の変化を含む）はその画素のインキのまま（α も変わらなければ 16 bit のまま）。変わった画素は、色の表の色はそのインキ、貸した層が見せていた色はそのインキ（そのまま写った色はインキのまま）、Genko の墨・白と規則が見せる色（墨・K だけの灰色・インキなし）は規則のインキ、ほかの灰色は規則（K だけ。Lab は L）、見せていた色から 1 チャンネル 2 以内の色（α だけ変わった画素の丸め）はその色のインキ、残り（混ぜた色・新しい線のふち）はプロファイル。高精度の RGB の画素はプロファイルで。
  - op がペイントレイヤーに絵として置いたもの（表示の絵として貼った絵・素材・動かした範囲の絵）は、高精度の層と同じくその場でインキに描く（色はページの規則）。
  - 既知の制限: 新しい色を描く操作で変わった画素は 8 bit の表示の色から戻す（16 bit のページでも）。塗りつぶしの境目は 8 bit の操作と同じく 72 dpi で調べる。フィルターと補正は下の「フィルターと補正」。
- **フィルターと補正**（工程の群C。利用者の決定 2026-10-14: 補正は画面の色に掛ける、フィルターはインキの版ごと）:
  - 補正（レベル・トーンカーブ・色相/彩度・反転・ポスタリゼーション・2階調化・グラデーションマップ・明るさ/コントラスト・露出。補正レイヤーと `filter_raster` の両方）は、インキが規則で意味する RGB に RGB のページと同じ式（高精度の補正の連続な式）を掛け、ページの規則でインキに戻す（`render/ink` の `meaning_of`・`inks_by_rules`・`correct`）。意味する RGB: K だけ（Lab は a = b = 0）の画素は灰色（K 100% は Genko の墨 0、インキなしは白）、色の表のインキはその RGB、ほかは表示の sRGB。戻し方: 8 bit の値ちょうどの色の表の色 → 墨・白 → 灰色は K だけ（Lab は L）→ プロファイル。補正が色を変えなかった画素（往復の丸め 1e-9 以内）はインキのまま（16 bit も）。補正レイヤーの不透明度・マスク・クリップは高精度の合成と同じ形で、インキの値で混ぜる。補正レイヤーの描画モードは COLOR-04 の `native.blend`（層の `blend` は Python のとおり見ない。PC2 の利用者の決定 2 で、描画モードのある補正レイヤーを省く扱いはやめた）。形を動かすフィルター・plugin の補正レイヤー（古い原稿）は高精度のページと同じく省いて記録（`adjust:…`。書き出しは `not_yet_ported`）。
  - フィルター（`filter_raster` のぼかし・シャープ・モザイク・移動ぼかし・放射ぼかし・ズームぼかし・波形・渦巻き・ゴミ取り・光彩拡散・ノイズ・線画抽出・雨）はインキの版ごとに、層の精度のまま掛ける（`render/ink_filters`）。動かす・ぼかす処理は α を掛けた値で（何も無い所に向かってぼけた線はインキのまま薄くなる）。明るさを変える処理はインキの形で: 暗くするのは K を足す（Lab は L を下げる）、明るくするのはインキを減らす（Lab は L を上げる）、コントラストは各版の平均のまわり（Lab の a・b は無彩色のまわり）、光彩は明るい画素（意味する色の明るさ。何も無い所は 8 bit の透明の画素と同じく暗い）の明るさを足す。モザイクは見本の画素の色（透明の見本は 8 bit と同じく黒）と元の α。新しく置く色（ノイズの粒・雨の筋・線画抽出の線・ゴミ取りの白と墨）はページの規則で（灰色は K だけ）。K だけの線はどのフィルターでも K だけのまま。大きさは高精度と同じく 200 dpi の画素を層の解像度に合わせる。範囲（`area`）はその中だけ。ペンの線・絵の層は先にページの規則でインキに描いてから掛け（8 bit の焼き込みと同じ。透明保護の層は自分の画素の中だけ）、掛けた層はペイントレイヤーになる。plugin のフィルターは 8 bit の絵を扱う外部の処理なので、群B の「表示の絵を貸す」方式で掛ける。
  - 画面: レベル補正・トーンカーブの窓のヒストグラムは、インキの層では意味する色の明るさで数える。
- **レイヤースタイル**（工程の群D）: インキのペイントレイヤーの効果は 8 bit の層と同じ形（効果の届く分だけ広く描いて切る）でインキに掛ける。水彩の縁は縁の α だけ Genko の墨へ寄せ（層の α はそのまま）、フチはその色の規則のインキを下に敷く（形は 8 bit の絵の α から）。表示の色（`color`）は画面ではその色の規則のインキ（α はそのまま。印刷では `color_prints` のときだけ）。トーン化（`screen`）は網点にするときだけ、インキが意味する灰色を 8 bit で網点にして規則で（K）。
- **取り込み**: CMYK のページへ RGB の絵はプロファイルで、CMYK の絵（PSD・JPEG）は絵のプロファイルからページのプロファイルへ（K を保つ。絵にプロファイルが無ければページのプロファイルとみなす）、Lab の PSD は Lab から変換して GKIR に。Lab のページへは Lab へ変換。RGB のページへの Lab の PSD は Pillow と同じ変換（Little CMS の Lab → sRGB）で読む（今までの断りを外す）。
- **画面**: 「ページ → 色モード…」（モード・精度・ICC の選択・意図・灰色の扱い・対象のページ）、ステータスにページの色モード。色の窓にペンの色のインキ（CMYK は %、Lab は L・a・b）と色域外の印（プロファイルを往復して CIE ΔE 1976 が 3 を超える色。色の表の色と灰色は出さない）。インキの値を選ぶと、その表示の RGB（規則がそのインキを当てる灰色・墨・白があればその色。無ければ表示の色を、Genko の墨と白、表で別のインキの色から 1〜数段ずらす）をペンの色にし、ページの規則がその RGB に別のインキを当てるときは、同じ色空間・同じプロファイルのページすべての色の表に組を入れる（`set_inks`、一つの取り消しで戻る）。スポイトはその点のインキ（見えている色はページを描いた値、描く先のレイヤーはその画素の値）を同じように選ぶ。値の欄は値を変えたときだけ選び直す（欄から出ただけでは何もしない）。

### COLOR-03 色モデル: RGB のプロファイル・グレー・32 bit、カラー設定・色の校正、チャンネル、特別な色モード（C++ 版。PhotoCraft の取り込み PC1a〜PC1d。利用者の決定 2026-10-16）

COLOR-01 の色管理と高精度。COLOR-02 の色モードを広げ、ページごとに RGB のプロファイルと精度（8・16・32 bit）、グレースケール、CMYK・Lab の 32 bit を持つ。形式は schema-v4.md の「色モデル（color-model@1）」。色モデルの無いページ（RGB・8 bit・sRGB）は今までどおり（Python 版と同じバイト・画素）。上流 PhotoCraft の色モード・深度・プロファイルの指定と変換（`image.mode.*`・`edit.assignProfile`・`edit.convertToProfile`）と問い合わせ（`document.inspect`・`document.pixel`）にあたる。上流の「文書」は Genko のページ。

- **内蔵のプロファイル**（PhotoCraft と同じ id。`native/src/core/data/profiles`、CC0。帰属は `native/third_party/photocraft/NOTICE.md`）: RGB の `srgb`（プロファイル無しと同じ）・`display-p3`・`adobe-rgb-compat`・`prophoto-compat`・`linear-srgb`・`rec2020`、グレーの `gray-gamma-2.2`・`sgray`、CMYK の `coated-cmyk`、Lab の `lab-d50`。別名（`p3`・`adobergb`・`prophoto`・`gray` など。大文字小文字・空白・記号は無視）と説明の文でも指せる。ほかに本が持つプロファイル（`"sha256:…"`）と ICC ファイル（`icc`: base64。16 MiB まで）。プロファイルは原稿に素材として埋め込む（内蔵のものも）。
- **モードと精度**（op `set_color_mode` を広げる。C++ 版だけの op）: `{"op": "set_color_mode", "page": int?（無ければ全ページと本の既定）, "mode": "rgb"|"gray"|"cmyk"|"lab"|"multichannel"（multichannel は PC1d）, "depth": 8|16|32?（既定 8。色モデルの無いページに高精度の層（COLOR-01 の `put_color_raster`）があれば、その層の一番高い精度: 黙って 8 bit に落とさない）, "profile": 内蔵の id・別名・"sha256:…"?, "icc": "<base64>"?, "intent": "perceptual"|"relative"|"saturation"|"absolute"?（既定 relative）, "bpc": bool?（黒点補正。既定 true）, "page_intent"?, "page_bpc"?, "gray": "profile"|"k"?（既定 profile）, "dither": bool?, "clip_hdr": bool?, "default": bool?}`。`intent`・`bpc` は変換のしかた。ページが持つ意図・黒点補正（要素の色をページに入れるしかた）は `page_intent`・`page_bpc`（省くと `intent`・`bpc` と同じ。PC1b）。
  - RGB: プロファイル（既定 sRGB）と精度。画素レイヤーは 8 bit なら PNG、16 なら高精度の u16、32 なら f32（HDR を保つ）。sRGB・8 bit・意図 relative・黒点補正ありなら色モデルの無いページに戻る（`color` を書かない）。
  - グレー: プロファイル（既定 `sgray`）。画素レイヤーは明るさ（0 が黒）1 版とアルファの GKIR。RGB からはプロファイル（意図・黒点補正）で変換する。ただしちょうど灰色（r = g = b）の画素は、ページが sGray か `gray: "k"` なら明るさ v/255 のまま（sGray の灰色 v は sRGB の (v, v, v) と同じ色。グレーから CMYK へ `gray: "k"` なら K だけ）。
  - CMYK・Lab: COLOR-02 のまま、32 bit（浮動小数）を加える。CMYK にはプロファイルが要る（内蔵の `coated-cmyk`、本のもの、ファイル）。Lab にはプロファイルを付けない。
  - 同じモード・同じプロファイルで精度だけを変えるときは値を写す: 8 → 16 は v × 257、8 → 32 は v / 255（バイト一致）、16 → 8 は四捨五入（`dither: true` なら決まった模様のディザ。RGB の 8 bit へ下げるとき。8 bit の値だったもの（v × 257）はディザでもその値のまま）、32 → 8・16 は 0..1 の値を量子化。違うプロファイル・モードへは Little CMS（意図・黒点補正）。透明度とマスクはそのまま。
  - HDR（32 bit の RGB・グレーの、0..1 の外の値）を残せない変換（8・16 bit へ、ほかのモード・プロファイルへ。グレーの HDR が残るのは同じプロファイルのグレー 32 bit と、sGray から sRGB の 32 bit（灰色を値どおり）だけ）は断る（「レイヤー … に HDR の値（0〜1 の外）があるので、このままでは変換できません（clip_hdr: true で切って変換します）」）。`clip_hdr: true` なら 0..1 に切って変換し、切った画素の数を `clipped` で返す。COLOR-02 の変換も同じ（高精度の f32 の層の HDR を黙って切らない）。
  - 断り（何も変えない）: ほかの色空間のプロファイル、Lab にプロファイル、CMYK にプロファイルが無い、読めない ICC、本の高精度の画素が 1 GiB を超える（変換の前に、層ごとの大きさから見積もって断る。大きな画素を作ってから断らない）、高精度で描くページ（16・32 bit の RGB、プロファイル付きの RGB は 8 bit でも）でまだ描けない層（高精度で合成できない描画モード、画素を持たない種類の層が持つ高精度の画素。`not_yet_ported`、層の名前を言う。トーンの層・形を動かす補正・書式を持つ高精度の線・線や絵を持つ層・フォルダーの中・v2 の線の層のラスターは PC2d から描く: COLOR-04「高精度・インキのページの合成の残り」。描画モードの補正層は PC2 の利用者の決定 2 で断らない）。インデックス・2 階調・ダブルトーン・マルチチャンネル（PC1d）は下の「特別な色モード」。
- **プロファイルの指定**（op `assign_profile`）: `{"op": "assign_profile", "page": int?, "profile": … | "none", "icc"?, "default": bool?}`。画素のバイトは変えず、ページのプロファイルだけを替える（見え方が変わる）。プロファイル付きになるページで描けない層があれば、`set_color_mode` と同じく断る。ページの色空間のプロファイルだけ（RGB・グレー・CMYK）。`"none"` は RGB で sRGB、グレーで sGray（CMYK には断る）。Lab のページは断る。全ページを指すと、その色空間のページと本の既定だけ（一つも無ければ断る）。`"default": true` はページを指しても本の既定に当てる（本の既定がほかの色空間なら断る。PC1b）。
- **プロファイルに変換**（op `convert_profile`）: `{"op": "convert_profile", "page": int?, "profile"|"icc", "intent"?, "bpc"?, "page_intent"?, "page_bpc"?, "dither"?, "clip_hdr"?, "default": bool?}`。見た目を保って、プロファイルの色空間へ変換する（モードはプロファイルの空間に、精度はページのまま）。`page_intent`・`page_bpc` は `set_color_mode` と同じ。`"default": true` はページを指しても本の既定（新しいページのモード）も変換する（全ページを指したときは前から本の既定も。PC1b）。
- Undo・Redo・保存・履歴は他の op と同じ。全ページへの `set_color_mode`・`assign_profile`・`convert_profile` は、ほかの人が押さえているページを一つずつ確かめる（`set_paper` と同じ）。
- **合成と表示**: プロファイル付きの RGB のページは、そのプロファイルの直線の光（トーンカーブを外した値）で合成する（`RgbSpace`）。画素（`raster_png`）は層の種類によらず（画素レイヤー、v2 の線の層のラスターなど）いつもページの値で、変換・描画・結合・貸し出し・書き出しは同じ一つの規則（`core::holds_page_values`）で決める。8 bit で描く要素（線・塗り・文字・フキダシ・枠など）の sRGB の色は、ページの意図・黒点補正でページの空間へ変換してから合成する（sRGB のちょうどの白と黒はページの白と黒）。層の色（`color`）・効果（縁取り・水彩の縁）・トーン化・モノクロの仕上げは sRGB の色で描く（効果とトーン化はその層の画素を先に sRGB にしてから）。画面へは相対的な色域を維持・黒点補正で sRGB にする。グレーのページは明るさで合成し、要素の色は規則（ページの色の表 → 墨は黒・白は白 → 灰色はその明るさ（sGray の値） → ほかはプロファイル）で当てる。sRGB のページの合成は前と同じバイト。
- **プロファイル付きのページの道具**: 新しい色を 8 bit の道具で描く op（ぼかし・ゆがみ・図形・塗りつぶし・グラデーション・隙間埋め・定規から・層の変換・プラグインのフィルターなど。COLOR-02 で CMYK・Lab のページに絵を貸す op と同じ）は、そのあいだページを sRGB のページとして（モードを外し、画素をその見えの sRGB にして）貸し、終わったら戻す。戻すとき、op が触れなかった層はバイトのまま、見えが前と 1 チャンネル 2 以内の画素は元の値（透明度だけ変わったものは新しい透明度）、貸した絵にあった色はその元の値（動かした色: sRGB の色域の外の色もそのまま）、ほかの色（op が持ち込んだ・混ぜた色）は sRGB からページの値へ（意図・黒点補正）。結合（`merge_down`・`merge_layers`・`merge_visible`・統合）は貸さず、ページの値をそのまま合成する（結果は高精度の層）。`paste`・塗り（`fill_area` など）は貸さない（絵と塗りは sRGB の要素としてページへ変換して描く）。焼き込み（フィルターの前、消しゴムの前）と下地混色はページの値で行う。
- **コピー・貼り付け・範囲の移動**: プロファイル付きのページの画素から切り取った絵（GUI のコピー、`transform_area` の持ち上げ）は、そのプロファイルを持つ（C++ 版だけの鍵 `rgb_profile`、保存しない）。op の後、同じプロファイルのページの画素レイヤー（線の層も）ではその値のまま画素に描き込み（画素は絵の下: 塗りは画素の上のまま）、ほかのページ・高精度の層・CMYK などではそのプロファイルから sRGB にして普通の絵にする。素材への登録も sRGB にする。本が持たないプロファイル（ほかの本から）の絵は sRGB とみなす。
- **グレーの補正**: グレーのページの補正層・補正は、どのプロファイルでも値どおりの灰色（明るさ）に掛けて値どおりに戻す（意味する色と戻しが往復で同じ。画面の見えはプロファイルで出す）。
- **予算**: 本の高精度の画素（GKCR）は合わせて 1 GiB まで（利用者の決定 2026-10-16。B4・600 dpi の f32 が入る）。素材 1 つの読み込みの上限 256 MiB と、メモリー・ディスクの確かめ・PERF-G はそのまま。op の後の本の確かめは、高精度の画素を素材ごとに一度だけ調べる（変わらないバイトをもう一度走査しない）。
- **問い合わせ**: `inspect`（snapshot）は色モデルを持つページにだけ、ページの `color`（原稿の JSON と、プロファイルの説明 `profile_description`。いつも UTF-8: ICC v2 の説明の ASCII の外のバイトは「?」、v4 の対になっていないサロゲートは U+FFFD）と層の精度（`precision`: `8`・`u16`・`f32`、GKIR はその精度。読めない画素の層には付けない）を加える（ほかの本の出力は変わらない）。`genko inspect <本> --pixel <ページ>:<x_mm>,<y_mm> [--layer ID] [--dpi N]`（C++ 版だけ。既定の dpi は原稿の dpi）: その点のページの値 `values`（RGB はプロファイルの 0..1、グレー・CMYK・Lab はインキ）、標本 `stored`（8・16 bit は整数、32 bit は float）、`alpha`、`srgb`。`--layer` はその層の画素。高精度の RGB のページの値は、層の値に、層の上に 8 bit で描いたもの（枠・台詞・効果線・ノンブル）の色をページの空間にして入れたもの。
- **書き出し**（形式に書けないものは `notes` で知らせる）:
  - PSD: グレーは Grayscale（色モード 1、8・16・32 bit）、色モデルのある RGB は RGB（色モード 3、8・16・32 bit）。ページのプロファイルを画像リソース 1039 に（sRGB のページは sRGB のもの）。CMYK・Lab の 32 bit は 16 bit で書く（Photoshop に 32 bit の CMYK・Lab は無い）。層もその精度で、RGB の層の sRGB で描いたものはページの空間へ変換する。32 bit はページの値の浮動小数（上流と同じ）。
  - TIFF: グレーのページは色が「自動」か「グレー」なら MinIsBlack（8・16・32 bit。32 は浮動小数 SampleFormat 3）とプロファイル。色モデルのある RGB のページは色が「自動」か「RGB」ならその値（8・16・32 bit）とプロファイル。CMYK・Lab の 32 bit は 16 bit。
  - PDF: グレーのページは ICCBased（N 1）、RGB のページはそのプロファイルの ICCBased（N 3）。精度は 8・16 bpc（32 bit は 16。HDR の値は 0..1 に切る）。
  - ページの値で書くもの（TIFF・PDF・PSD）は、ページの値を高精度の画素と同じ形で持つため、1 ページ 67,108,863 画素（`kColorRasterMaxPixels`）まで。それを超える解像度は、大きな確保の前に `image_too_large` で断る（例: A3 は 600 dpi で超える。解像度を下げるか PNG・JPEG で書き出す）。
  - PNG・WebToon・SNS・EPUB・Kindle・strip・layers・アニメーションなど: 表示の sRGB（layers のプロファイル付きのページの画素レイヤーも、その値を sRGB にして書く）。
  - `notes`: 画面の色から書いたページが CMYK・Lab だけなら COLOR-02 の言葉、グレーや RGB の色モデルを含むなら「色モード・プロファイルを持つページ N ページは、この形式・色ではその値のまま書けないため、画面の色（sRGB）から変換して書き出しました」（入稿セットは PNG のこと）。32 bit を 16 bit にしたときは「32 bit のページ N ページは、この形式では 16 bit にして書き出しました」。PDF で HDR の値（0..1 の外。高精度の画素・グレーの明るさ、露出の補正層で出るものも）を持つ 32 bit のページを書いたときは「HDR の値（0〜1 の外）を持つ 32 bit のページ N ページは、PDF では 0〜1 に切って書き出しました（HDR のまま残すには TIFF か PSD で書き出します）」も足す。CLI（JSON の `notes`、ふつうの出力では標準エラー）・MCP の `export`・HTTP の `/v1/export`・正式な書き出しが同じものを返す。

- **選択範囲**: 区域の言葉に `{"channel": id か名前}`（チャンネルの濃度をマスクに。`invert`・`grow_mm`・`feather_mm` も他の区域と同じ）。選択範囲をチャンネルに保存は `add_channel` の `fill: area`。
- **描く先（画素の op の `channel`）**: 画素の op（`add_stroke`・`erase`・`erase_raster`・`fill`・`fill_area`・`fill_enclosed`・`flood_fill`・`gradient_fill`・`filter_raster`・`delete_area`・`transform_area`・`smudge`・`liquify`・`add_shape`・`fill_gaps`）に C++ 版だけの任意の引数 `"channel"`:
  - アルファ・特色チャンネル（id か名前）: そのチャンネルを見えない画素レイヤー（濃度を明るさにした不透明な灰色。コマからはみ出す）として op に貸し、op の後で明るさ（透明にした所は黒）を濃度に戻す。貸すのはチャンネルの解像度によらず画素レイヤーと同じ 200 dpi（画素の op はどれも 200 dpi で位置・幅を数えるため。600 dpi の特色は 3×3 の平均で貸す）。戻すときは op が変えた画素だけを、チャンネル自身の解像度へ、その画素が覆う割合で入れる（チャンネルの方が細かいときは双一次）。変えた画素の届かない所は元の値のまま（16 bit も）、何も変えなかった op ではチャンネルのバイトもそのまま。明るさはグレーのページの規則: Genko の墨（灰色 0・10・15・20。ペンの既定・色見本の黒）は 0、白は 1、ほかの灰色 v は v/255。ページの層は変わらない。16・32 bit のチャンネルでは変えた画素が 8 bit の段になる: そのときは op の結果に `"channel_precision": 8` を返す。
  - 色の版（red・cyan など）: op の後で、その層のほかの版と透明度を変わった画素だけ元に戻す（上流 restrict_to_color）。ペイントのレイヤーだけ（ペンのレイヤーは断る）。線や絵は先に画素に焼き込む。
  - `"composite"` と無しは今までどおり。Python の op の引数の扱いは変えない: ページのチャンネル・色の版・`"composite"` のどれも指さない値（ページに無い名前、数、null）は、Python が知らない引数を扱うとおり無視して「unknown keys ignored: channel」の警告を出す（op は断らず、層に描く）。`filter_raster` のレベル補正・トーンカーブ・明るさ・コントラスト（`levels`・`curve`・`brightness_contrast`）の `channel` は Python のもの（r・g・b、ほかは 3 色すべて。"red" やチャンネルの名前も 3 色）で、そこで描く先になるのはアルファ・特色チャンネルの id と、CMYK・Lab のページ（Python に無いページ）の色の版の名前だけ。
  - AI と進める原稿の規則（strict_gates）は描く先で決める: アルファチャンネルは印刷に出ないのでネームの承認の前でも描ける、特色チャンネルは印刷に出るので承認の後（「… on a spot channel (printed) needs name_ok …」）、色の版はその層の規則。
  - 画面からは、描く先をウィンドウの画素の op とそのプレビューの両方に付ける（プレビューと適用が同じ）。レベル補正・トーンカーブ・明るさ・コントラストでは、op が色を指していない（すべて）ときだけ、RGB のページの版を r・g・b、CMYK・Lab のページの版をその名前、チャンネルを id で付ける。
- **ページの操作**: 判型の変更（`set_page_spec` の move）でチャンネルもレイヤーと同じく基本枠に合わせて動かす（その解像度のまま新しい紙に）。ページの複製・取り込みはチャンネルごと運ぶ。ページの色モードの深度が変わるとチャンネルの精度も合わせる（8 → 16 は v × 257）。
- **表示**: 特色はページの絵の上に、特色を合成したときと同じ式 `p + (s·c + (1 − s)·p·c − p)·v` で刷る（画面・PNG などの書き出し・`genko render`。RGB・グレー・CMYK のどのページでも画面の色で。上流のマルチチャンネルの表示の式 `(1 − s·v)·p·(1 − v + v·c) + s·v·c` は 0 < s かつ v < 1 で合成の結果と違うので使わない: 例えば白に黒インキの s = 1・v = 0.5 は、画面も合成も 50% の灰色）。チャンネル パネルの見え方（保存しない）: 色の版を隠す（1 版だけなら灰色で）、アルファを重ねる（色・不透明度・色を付ける所）、特色を刷らない。部分を描いても全体を描いても同じ画素。
- **問い合わせ**: `inspect`（snapshot）はチャンネルを持つページにだけ `channels`（id・名前・種類・色・不透明度と色を付ける所、または濃度・精度・画素の大きさ）を加える。素材が壊れて読めないチャンネル（原稿は読み取り専用で開き、読んだときの問題として報告される）は `"size": null` と `"problem"`（読めない理由）を付けて並べ、ほかはいつもどおり。描くときは読めないチャンネルを無い（濃度 0）として描き、全体を失敗にしない。
- **書き出し**:
  - PSD: アルファ・特色チャンネルを統合画像の色の版の後ろに追加チャンネルとして書く（パネルの順。統合画像には特色を刷らない）。名前は画像リソース 1006（ASCII）と 1045（Unicode）、見え方は 1077（DisplayInfo: 版 1 の後に 1 チャンネル 13 バイト — RGB の色・不透明度または濃度の %・0 選択範囲／1 マスク範囲／2 特色。1007 と違って種類の後の埋めのバイトは無い。GIMP と psd-tools は 13 バイトで読み、14 バイトのものを psd-tools は読めない）。どの色モードのページでも。
    - 標本の向き: Photoshop がチャンネルを灰色で見せるとおり、色（インキ・重ねの色）の付く所が暗い。特色は 最大値 − 濃度（0 がインキ 100%）、色を付ける所が「選択範囲」のアルファは 最大値 − 濃度（0 が選ばれた所）、「マスク範囲」のアルファは濃度（最大値が選ばれた所）。根拠: PSD の CMYK の版は 0 がインキ 100%（Adobe の仕様の色の構造「0 = 100% ink」、Genko の CMYK の PSD の書き手、Pillow・psd-tools の読み手が反転する）、上流 PhotoCraft 自身の multichannel_map.rs の「Photoshop がチャンネル パネルで見せるとおり 0（黒）= インキ 100%」、psd-tools の 1077 の種類の名前（0 ALPHA・1 INVERTED_ALPHA・2 SPOT）と全体のマスクの種類「0 = 色が選択範囲、つまり反転」、GIMP は自分のチャンネル（白 = 選ばれた所）を種類 1 で書く。上流は RGB・CMYK の文書の特色と「選択範囲」のアルファを濃度のまま書く（逆向き。意図的な違い）。psd-tools（GENKO_PYREF の venv の 1.10.9）で読むと、名前・種類・色・不透明度と標本がこの向きのまま読め、追加チャンネルを透明度とはみなさない（レイヤーがあるため）。
  - PDF: 特色は `/Separation`（インキの名前、代わりの色は DeviceRGB のインキの色）の画像としてページの絵の上に重ね、オーバープリント（`/OP true /op true /OPM 1`）・乗算（`/BM /Multiply`）。画像の標本は濃度そのもの（透明を扱わない RIP でも版は濃度のまま）、ソフトマスク（`/SMask`、DeviceGray）は濃度 0 の所が 0・ほかは 255。オーバープリントを再現する描き手は特色の版として分け、再現しない描き手（Acrobat の既定・ブラウザー・Preview・事務用のプリンター）はインキの色を絵に掛け合わせて見せ（画面の solidity 0 の見え方）、インキの無い所はページの絵がそのまま見える（以前は濃度 0 を白で塗って絵を隠した）。ソフトマスクを濃度そのものにしないのは、透明を合成する RIP で版が濃度の 2 乗になるため。PDF が決まった意味で使う版の名前（All・None・Cyan・Magenta・Yellow・Black。大文字小文字によらず）の特色は「<名前> Spot」（使われていれば「<名前> Spot 2」…）の名前で書き、notes で知らせる。solidity は書かない（画面の見え方だけのもの）。アルファは書かない（notes）。
  - TIFF・PNG など: 特色は画面の見え方で刷り込む（インキ・値のまま書いた TIFF には書かない）、アルファは書かない。どちらも `notes` で知らせる。
- **画面**: チャンネル パネル（表示 → チャンネル。レイヤーのタブの隣）: 合成・色の版・アルファ・特色（目・縮小図・名前）・ストック（ページに残した選択範囲。クリックで選択範囲に）。行のクリックで描く先にする（アルファ・特色はそのチャンネルだけを灰色で、色の版はその版だけを灰色で見せる。上流と同じ）。ボタン: 新規（アルファ。作ったものを描く先に）・特色（選択範囲があればその所）・複製・削除・選択範囲として読み込む・選択範囲を保存。メニュー: チャンネルのオプション…（ダブルクリックでも）・チャンネルを分割（確かめてから）・チャンネルを統合…（このページから続くグレーのページ）・特色チャンネルを合成。描く先は Ctrl+Alt+2（合成）・Ctrl+Alt+3…9（色の版、次にチャンネル。Ctrl+2 は定規にスナップのまま）。描く先はウィンドウとページごとに覚え、窓から送る画素の op に `channel` を付ける。選択 → 選択範囲をチャンネルに保存…・チャンネルから読み込む。
- **既知の制限**（PC1c）: チャンネルに描くときの貸し出しは 200 dpi・8 bit の灰色（原稿の dpi の特色で op が変えた所は 200 dpi の細かさになり、16・32 bit のチャンネルでは変えた画素が 8 bit の段になる。結果の `channel_precision` で知らせる）。上流のクイックマスクのチャンネルは無い（Genko のクイックマスクは表示だけ）。画像操作（Apply Image・Calculations）は COLOR-04 の PC2c で入った（チャンネルを元にも先にもできる）。特色を合成した後の枠・台詞は統合した層の上に描くので、特色は枠と台詞の下になる。PDF のオーバープリント・乗算・ソフトマスクは poppler（pdftoppm）で描いて確かめた（インキの無い所に絵が見える・インキの所は掛け合わせ）が、実機の Acrobat と RIP では確かめていない（PSD-01 と同じ但し書き）。PSD の追加チャンネルの標本の向きと 1077 の形は上の根拠と psd-tools・GIMP の読み方から決めたもので、実機の Photoshop では確かめていない。

#### 特別な色モード（PC1d: インデックスカラー・カラーテーブル・2 階調・ダブルトーン・マルチチャンネル・色版の削除。利用者の決定 2026-10-16）

上流 PhotoCraft の `image.mode.indexedColor`・`image.mode.colorTable`・`image.mode.bitmap`・`image.mode.duotone`・`image.mode.multichannel` と、色の版の `channel.delete`（残りの版でマルチチャンネルに）にあたる。形式は schema-v4.md の「色モデル（color-model@1）」の 5 つの形（`indexed`・`bitmap`・`duotone`・`multichannel` と GKIR の Multichannel）。上流の「文書」は Genko のページ。どの op も C++ 版だけ（公開の `genko schema` と MCP の道具の表は Python のまま）。Undo・Redo・保存・履歴・GC は他の op と同じ。失敗したら何も変えない（バッチ全体を戻す）。言葉は wording.cpp で日本語。色モデルの無いページ（RGB・8 bit・sRGB）は今までどおり（Python 版と同じバイト・画素）。

- **統合（利用者の決定: 上流どおり）**: インデックスカラー・2 階調・マルチチャンネルへの変換は、先にページの画素レイヤーを Genko の「画像をフラット化」（`merge_visible` の `flatten`。最初に見えている層へ、紙の上で合成）と同じ規則で 1 枚に統合する。コマ・台詞・フキダシ・効果線などの要素と、ネーム・下描きの層は要素・層のまま残す（上流は文書を 1 枚の層にする。意図的な違い）。ネーム・下描きの層は印刷しないので、画素も元のまま持つ（表の色・2 値に寄せない。画面ではページの最後の合成の写像で、表の色・2 値に見える）。統合した数を結果の `"flattened"`（ページの数）で返す。統合は「画像をフラット化」と同じく非表示の層を捨てる: 中身（画素・線・パッチ・塗り・補正）のある非表示の層を捨てたときは、その数を結果の `"discarded"` で知らせる（0 のときは書かない。特色の合成 `merge_spot_channel` も同じ）。AI と進める原稿の規則（strict_gates）は統合にも当てる。ダブルトーン・カラーテーブルは統合しない（上流も画素を変えない）。マルチチャンネルのページをマルチチャンネルにし直すとき（精度だけ）は統合しない。
- **`to_indexed`**: `{"op", "page"?（無ければ全ページと本の既定）, "palette": "selective"|"perceptual"|"adaptive"|"exact"|"systemMac"|"systemWindows"|"web"|"uniform"?（既定 selective）, "colors": 2..256?（既定 256）, "forced": "blackWhite"|"none"|"primaries"|"web"?（既定 blackWhite）, "transparency": bool?（既定 true）, "dither": "diffusion"|"none"|"pattern"|"noise"?（既定 diffusion）, "amount": 0..100?（既定 75）, "default": bool?, "clip_hdr": bool?}`（引数と既定は上流 mode_cmds.rs:182-208）。RGB・グレー・ダブルトーン・CMYK・Lab・インデックスのページから（上流の enabled と同じ。2 階調・マルチチャンネルは断る）。ページを統合し、sRGB・8 bit でなければページ自身の意図・黒点補正で sRGB 8 bit にして（結果の `converted`、HDR は `clip_hdr` で切る。切った数は `clipped`）、統合した層の画素からパレットを作り（上流 algo/src/quantize.rs をそのまま移した `render/quantize`。`exact` は色が 256 を超えると断る）、ディザで量子化する。`transparency` で α が 0.5 未満の画素があれば表の最後に透明の番号（白）。結果 `{"colors", "transparent", "flattened", "discarded"?, "converted", "clipped"?, "pages"?（2 ページ以上のとき各ページの colors・transparent）}`。全ページのときの本の既定は最初のページの表。
- **`set_color_table`**: `{"op", "page"?, "table": "custom"|"blackBody"|"grayscale"|"spectrum"|"systemMac"|"systemWindows"|"web"?（既定 custom: 今の表）, "colors": ["#rrggbb" | [r,g,b], …]?（1..256）, "entries": {"番号": 色}?, "transparent": 番号|null?}`。インデックスのページだけ（ほかは断る。全ページなら インデックスのページと本の既定だけ）。印刷する画素レイヤーの画素は「古い表で最も近い番号 → 新しい表のその番号の色」（新しい表に無い番号は新しい表で最も近い色。上流 mode_cmds.rs:254-321）、新しい透明の番号になった画素は透明。ネーム・下描きの層の画素は元のまま（画面では新しい表の色に見える）。結果は新しい表（`{"colors", "transparent"}`）。
- **`to_bitmap`**: `{"op", "page"?, "method": "diffusion"|"threshold"|"pattern"|"halftone"?（既定 diffusion。`threshold50` は threshold）, "frequency": 1..999?（既定 53。線/インチ）, "angle": -180..180?（既定 45）, "shape": "round"|"ellipse"|"line"|"square"|"diamond"|"cross"?（既定 round）, "default"?}`。グレーのページだけ（ダブルトーン・2 階調・ほかのモードは断る。上流と同じ）。ページを統合して 8 bit にし（HDR は白に切る）、白の上で合成した明るさを方法で 0/1 にする（上流の to_bitmap。網点のセルは統合した層の解像度（200 dpi）÷ 線数）。ページは 2 階調（8 bit の Gray。統合した層は標本 0/255・α 255、ネーム・下描きの層は元の値のまま）になり、方法・線数・角度・形を記録する。結果 `{"flattened", "discarded"?}`。`set_color_mode mode=gray` でグレーに戻る（画素はそのまま、失うものは無い）。
- **`set_duotone`**: `{"op", "page"?, "type": "monotone"|"duotone"|"tritone"|"quadtone"?（既定 duotone。インキ 1〜4）, "inks": [{"name"?, "color"?: "#rrggbb"|[r,g,b], "curve"?: [[in,out], …]}]?, "default"?}`。グレーかダブルトーンのページだけ（全ページならそのページと本の既定だけ）。既定のインキは上流の Black (0,0,0)・Warm Brown (158,97,46)・Gold (219,173,46)・Slate Blue (69,97,148)、曲線は直線。曲線は 2〜13 点（入力で並べ替える。1 点以下はそのインキの曲線のまま）、入力・出力 0..100、入力は狭義増加。画素は変えない。結果 `{"inks": [名前…]}`。`set_color_mode mode=gray` でインキが外れる。
- **マルチチャンネル**（`set_color_mode` の `"mode": "multichannel"`、`depth` は省けばページのまま）: RGB（sRGB。プロファイル付きの RGB は「sRGB へ変換してから」と断る）・CMYK・Lab・グレー・ダブルトーンのページから（インデックス・2 階調は断る）。ページを統合し、版に分ける（上流 multichannel_cmds.rs:97-119）: RGB → Cyan・Magenta・Yellow（各 1 − 値）、CMYK → Cyan・Magenta・Yellow・Black（そのまま。プロファイルを保つ）、Lab → Alpha 1・Alpha 2・Alpha 3（1 − 符号化した値）、グレー → Black（濃度 1 − 明るさ。プロファイルを保つ）、ダブルトーン → インキごとの版（濃度を各インキの曲線に通す）。版の表示色は上流の CYAN (0,174,239)・MAGENTA (236,0,140)・YELLOW (255,242,0)・プロセスの BLACK (35,31,32)、Lab とグレーの版は黒。アルファ・特色チャンネルはそのまま。戻すとき（`set_color_mode`）、版の数がモードと合えば読み替え（3 → RGB・Lab、4 → CMYK、1 → グレー。1 − 値・そのまま）、合わなければ刷った見え（sRGB）から変換する（上流 151-199）。結果は `set_color_mode` のものに `"flattened"`（と `"discarded"`）。
- **色の版の削除**（`delete_channel` に色の版の名前・ラベル）: RGB・CMYK・Lab・グレー・ダブルトーンのページは `"to_multichannel": true` のときだけ（無ければ断る）、ページを上のとおりマルチチャンネルにしてからその版を除く（Photoshop の動き。上流の `channel.delete` はアルファだけを消し、版を減らすのは試験の中だけ）。マルチチャンネルのページはそのまま版を除く。版が 1 つしか残らないページ・最後の版は断る。各層の画素からその版を、`inks` からその値を除く。結果 `{"plates": 残りの数}`（変換したときはその結果も）。
- **ほかの op との関係**: `set_color_mode` の `mode` に indexed・bitmap・duotone は無い（それぞれの op で作る）。`assign_profile` はインデックス（sRGB 固定）・マルチチャンネル（版にプロファイルは無い）のページを断る（2 階調・ダブルトーンはグレーのプロファイルを替えられる）。`convert_profile` は 4 つのどのモードも断る（`set_color_mode` で戻してから）。マルチチャンネルのページは色相・彩度・カラー・輝度の描画モードを合成できない（その層があれば変換を断り、読んだ原稿は読み取り専用）。インデックスのページは 8 bit の画素（`raster_png`）だけを持つ: 高精度の画素（`color_raster`）を置く op（`put_color_raster` など）は断り、そういう層のある原稿は読み取り専用。どの op の後も、包み（`ops_registry`）が op の変えた層だけを次のように寄せる（変えなかった層はバイトのまま）:
  - 2 階調のページ: 変えた画素レイヤーの GKIR の標本と α を 50%（128）で 0/255 に。
  - インデックスのページ: 変えた画素レイヤーの画素の色を表の最も近い色に（ディザなし、α はそのまま）。
  - 2 階調・インデックスのページのネーム・下描きの層（印刷しない）は寄せない: 画素は描いたまま持ち、画面ではページの最後の合成の写像（下の「描画」）で表の色・2 値に見える。
  - 16・32 bit の RGB のページ（インデックスでない）: op が新しく作った 8 bit の画素（`put_raster` の PNG など）を、高精度で持てる層（ペイントの層、線・パッチ・トーン・パネルの切り抜き・効果・層の色の無いもの。高精度のページの規則と同じ）ならその精度へ正確に広げる（v × 257、v / 255。design 4.5、PC1a の既知の制限を閉じる）。持てない層は 8 bit のまま。`assign_profile` はバイトを変えないので広げない。
- **描画**（画素ごとの写像だけなので、部分を描いても全体を描いても同じ画素）:
  - インデックス: 最後の合成（要素、画面ではネーム・下描きの層も含む）を表の最も近い色に（ディザなし。上流 mode.rs:22-31）。
  - 2 階調: 最後の合成の明るさを 50% で 0/1（アンチエイリアスの付いた要素、画面ではネーム・下描きの層も 1 bit で見せ、書き出しと一致）。
  - ダブルトーン: 灰色の濃度（1 − 明るさ）を各インキの曲線に通し、白の上にインキを掛け合わせて刷る（上流 mode.rs:73-117）。要素の色はグレーの規則。
  - マルチチャンネル: 版ごとに (1 − 濃度) で分離できる描画モードの式で合成し（CMYK と同じ考え）、版を白の上に上流の式 `(1 − s·v)·p·(1 − v + v·c) + s·v·c`（s は版の solidity、既定 0）で刷る（上流 compose/src/multichannel.rs:14-38）。要素の色: ① ページの `inks` ② 灰色（Genko の墨 0・10・15・20 は濃度 1）は `key` の版（曲線があれば通す。RGB からは C・M・Y、CMYK・グレーからは Black、Lab からは Alpha 1、ダブルトーンからは各インキ）③ 残りは元のモードの規則（RGB は 1 − 値、CMYK はプロファイル、Lab は D50（灰色は a = b = 0 で変換）、グレー・ダブルトーンはプロファイルの灰色を ② の版に）。
  - ディザは変換の op のときだけ。浮動小数の pow・cbrt は `render/libm_float`（glibc と同じ値）で決定的（量子化の Lab も）。上流 algo の試験と、上流の Rust で作った固定のハッシュ（`test_quantize`）でビットまで同じことを確かめる。
- **問い合わせ**: `inspect` の色モデルの `mode` は indexed・bitmap・duotone・multichannel、`--pixel` は同じ名前と、インデックスのページでは `index`（表の番号）、マルチチャンネルでは版ごとの濃度を `values`。
- **書き出し**（形式に書けないものは `notes` で知らせる）:
  - PSD: 2 階調は Bitmap（色モード 0、1 bit。1 が黒）、インデックスは Indexed（色モード 2、768 バイトの色の表、画像リソース 1046 色の数・1047 透明の番号）。どちらも PSD の制約でレイヤーを持てないので統合画像だけ（notes。チャンネルも書けない）。マルチチャンネルは Multichannel（色モード 7）の統合画像で、版をインキの所が暗い（最大値 − 濃度）チャンネルとして名前（1006・1045）と見え方（1077、種類 2 特色）を付けて書く（PC1c の特色の向きと同じ。32 bit は 16 bit にして notes）。ダブルトーンはグレー（色モード 1）の値で書き notes（インキと曲線は書かない。Photoshop の Duotone（色モード 8）の 1026 の形を確かめられないため安全な方）。
  - TIFF・PDF の 2 階調・インデックスは、グレー・RGB のページの値で書くときと同じく色で決める: 2 階調は色が「自動」か「グレー」のとき、インデックスは「自動」か「RGB」（コマンドラインの既定）のとき、そのモードで書く。ほかの色では画面の色から変換して書く（PC1a の notes）。
  - TIFF: 2 階調は 1 bit（既存の 2 値。Group 4）、インデックスはパレット（Photometric 3、ColorMap は v × 257、LZW）。ダブルトーンは色が「自動」か「グレー」ならグレーの値＋notes、ほかの色なら刷った見え（sRGB）＋notes。マルチチャンネルは刷った見え（sRGB）＋notes。
  - PDF: 2 階調は 1 bpc の DeviceGray、インデックスは `[/Indexed /DeviceRGB n−1 <表>]`。ダブルトーン・マルチチャンネルは刷った見え（sRGB）＋notes。
  - PNG・WebToon・SNS・EPUB・Kindle・strip・layers・アニメーションなど: 表示の sRGB（2 階調・インデックスは表示の写像のまま）。ダブルトーン・マルチチャンネルは notes（「… この形式ではダブルトーンのインキのまま書けないため、刷った見え方（画面の色、sRGB）で書き出しました」「マルチチャンネルのページ N ページは、この形式では版のまま書けないため …（PSD なら版のまま書けます）」）。
- **画面**: ページ → 色モード に「2 階調…」「インデックスカラー…」「ダブルトーン…」「マルチチャンネル」（モードの印に入る）と「カラーテーブル…」（インデックスのページだけ）。新しい `app/mode_dialogs.cpp`: インデックスカラー（対象・パレット・色数・強制する色・透明部分を残す・ディザとその量）、カラーテーブル（16×16 の色の格子、クリックで色を選ぶ・表・透明にする色）、2 階調（対象・方法・線数・角度・網点の形。グレーのページだけ）、ダブルトーン（対象・種類・インキごとの名前・色・カーブ「入力:出力」2〜13 点）。統合を伴う変換は、統合される層のうち画素・線・パッチ・塗り・補正を持つものが 2 枚以上か、捨てる非表示の作画レイヤーが 1 枚でもあれば「画像を統合」を確かめる（「画像をフラット化…」と同じ言葉で「非表示の作画レイヤー（N 枚）は破棄します（ネーム・下描き・コマ枠は保持）」、要素は残ること・取り消しで戻ることも書く。ページの空の役割の層だけなら聞かない）。対象を「すべてのページ」にしたときは、どれかのページに捨てる非表示の層があれば確かめる（統合することはダイアログに書いてある）。チャンネル パネルで色の版を削除すると、マルチチャンネルでないページはマルチチャンネルになること（と、同じ言葉で捨てる非表示の層）を確かめてから `delete_channel` に `to_multichannel: true`（版が 1 つなら断る）。パネルの見出しは「マルチチャンネル」と版の名前。ステータスにモード（「インデックスカラー（N 色）」「2 階調」「ダブルトーン」「マルチチャンネル（N 版）」）と、ポインターの下の値（`genko inspect --pixel` と同じ関数 `render::pixel_at`。150 ms ごと、原稿の dpi（300 まで）。RGB・CMYK・Lab・グレー・版の値、インデックスは番号と色）。色の窓はマルチチャンネルのページで版ごとの欄、インデックスのページで今の色の表の番号。
- **上流との違い**（意図的）: ページを上流の文書に読み替える。統合しても要素（コマ・台詞・フキダシ・効果線）とネーム・下描きの層は残し、描くたびにページの規則で当てる（上流は 1 枚の層だけ）。Genko の統合は紙の上で合成するので統合した層は不透明になり、`to_indexed` が透明の番号を作ることは普通は無い（`set_color_table` の `transparent` で後から決められる）。網点のセルは原稿の dpi でなく統合した層の解像度（200 dpi）から。2 階調の画素は Gray 8 bit の 0/255（上流は 1 bit の Bitmap の文書）。マルチチャンネルの版は濃度（0 = インキなし）で持つ（PSD はインキの所が暗い向きで書く）。ダブルトーンは PSD のグレー（色モード 1）＋notes。Pantone の既定のインキは持たない（上流と同じ一般の名前）。色の版の削除でマルチチャンネルにする op（`delete_channel` の `to_multichannel`）は上流に無い（Photoshop に合わせた）。
- **既知の制限**（PC1d）: インデックス・2 階調のページで描いた結果は表・2 値へ寄せるだけで、道具の色の選び方は 8 bit のまま。PSD のインデックス・2 階調・マルチチャンネルはレイヤーを持てない（統合画像だけ）。ダブルトーンの PSD・TIFF にインキと曲線は書かない。マルチチャンネルの PSD・版の向き・1077 の形は psd-tools で読んで確かめたもので、実機の Photoshop では確かめていない。
- **台帳**: image.mode.indexedColor・image.mode.colorTable・image.mode.bitmap・image.mode.duotone・image.mode.multichannel・channel.delete（色の版から マルチチャンネルへ）。document:color-depth-model は色モデル・深度・チャンネルの部分の証跡を足し、高精度でまだ断っている処理（page.cpp の `not_yet_ported` など）が残るので開けたまま。

### COLOR-04 補正と色管理（C++ 版。PhotoCraft の取り込み PC2。利用者の決定 2026-10-17）

上流 PhotoCraft の補正（`image.adjustments.*`・`layer.newAdjustmentLayer.*`・`layer.setAdjustment`・自動補正）、色管理の残り、補正と同じ仕組みを使う画像の操作（画像操作・演算・トラッピング・フェード）を取り込む。形式は schema-v4.md の「補正（adjustments@1）」。**Python の形の補正**（Python の種類に Python のキーだけ。`native` を持たない）は今までどおり（Python 版と同じ JSON・表・バイト・画素。`features` も増えない）。工程は PC2-0（土台。この節の骨組み）と PC2a〜PC2d（各種類の式・画面・PSD。各群がこの節に書き足す）。

- **土台**（PC2-0）: 補正はどれも 1 つの関数（`core/adjust.hpp` の `AdjustFunction`: ページの符号化した RGB の値と画素の位置 → 補正後の値。表で書けるものは 256 の表、CMYK・Lab・グレーの版に直接掛ける組も持てる）で 3 つの道に渡す（ARCHITECTURE.md §4a）。Python の形は今の連続な式（`PreciseAdjustment`）がその 1 つ。種類の表（`core/adjust_kinds`）に全部の種類の名前・設定（キーの順・既定・範囲）・中身を書く群を置く。中身（式）がまだ無い種類・設定・op は使う所で断る（`not_yet_ported`、種類か op の名前と群を言う）。保存されていれば形だけ確かめ、描くときは省いて記録（`adjust:<種類>`。書き出しは断る）。
- **`native`**（Python の種類に C++ 版だけの設定を 1 つの物で。`{"kind": "levels", …, "native": {…}}`）: どの種類も `blend`（Genko の 20 の描画モード）。`levels`・`curve` は `method`（`genko`: Python の式、既定 | `upstream`）、`space`（`rgb`|`cmyk`|`lab`|`gray`。チャンネルの組の空間）、`channels`（チャンネルごとの組。levels は `{black 0..253, white 2..255（black + 2 以上）, gamma 0.01..9.99, out_black, out_white 0..255}`、curve は 0..255 の点 2〜19 個）。`brightness_contrast` は `method`（`modern`|`legacy`）、`posterize` は `method`（`floor`）、`gradient_map` は `reverse`・`dither`（bool）。op が受け取ると、渡したキーだけを表の順に置く（組の空間は書かなければページから: CMYK は cmyk、Lab は lab、グレーは gray、ほかは rgb）。何も言わない `native`（空・null）は外す（Python の形のまま）。知らないキー・型の違い・範囲外・非有限・ページが合成できない描画モード（Lab・マルチチャンネルは層と同じ）は op を断り、保存された原稿は読み取り専用で開く。
- **C++ 版だけの種類**（設計 2.3。保存は既定を埋めた正規形、キーは表の順。範囲外は切る、型の誤り・非有限は断る）: 補正レイヤーと `filter_raster` の両方に `hue_saturation`・`vibrance`・`color_balance`・`black_white`・`photo_filter`・`channel_mixer`・`selective_color`（PC2b）、`color_lookup`（PC2a）。`filter_raster` だけに `desaturate`（PC2b）、`equalize`（PC2a）、`shadows_highlights`・`replace_color`・`match_color`（PC2c。画素の周りを見る局所の補正）。

  - **op `auto_adjust {page, id, mode, area?, channel?}`**（`image.autoTone`・`autoContrast`・`autoColor`、上流 edit_cmds.rs）: 層の見えている画素（選択範囲の中）の R・G・B の度数から、両端 0.1% を切った黒と白を求める。`tone` はチャンネルごと、`contrast` は 3 つをまとめた同じ点（色は変えない）、`color` はチャンネルごとの点と、各チャンネルの中央値を 3 つの平均へ動かすガンマ（0.1〜9.99）。結果はレベル補正の組（`native: {method: upstream, space: rgb, channels}`）として `filter_raster` で掛ける（`channel`・`area` は `filter_raster` と同じ）。マルチチャンネルのページは組を持てず色の意味も無いので、どの `mode` も 3 つをまとめた点を合成の組（`black`・`white`・`gamma`、`native: {method: upstream}`）で掛ける。返事は `{"levels": 組}`。
  - **PSD**（利用者の決定 5、`render/psd_adjust`。上流 io/adjust_map.rs・gradient_bake.rs）: 書き出しは補正レイヤーを `levl`（合成と、ページの色空間のチャンネルの組）・`curv`（合成とチャンネルの曲線と、Photoshop の書く `Crv ` の部分。Python の形のガンマの曲線・19 点を超える曲線は Photoshop の点に直す）・`brit`（`CgEd` の記述子を添えて。Python の形は従来の式として）・`post`・`thrs`（`bitonal` も 2 階調化として）・`nvrt`・`expA`・`grdm`（色の止まり・逆・ディザ）・`clrL`（表を .cube の中身で。四面体は三線形になる）として書き、近似して書いたものは書き出しの知らせ（`notes`）に日本語で言う（ページと違う色空間の組は書かない、1 色だけに掛ける形は全体に、など）。読み込みは同じ鍵を補正レイヤーに（レベル補正・トーンカーブは `native.method: "upstream"`、ページの色空間のチャンネルの組、描画モードは `native.blend`。ページで持てない描画モード・組は外す）。表の読めない `clrL` などは今までどおり省いて `skipped`。
  - **CLI**（C++ 版だけ。公開の `genko schema`・MCP の書き出しの表は変えない）: `genko export <原稿> <出力> --format cube [--page N] [--lut-size 2..256] [--title 名前] [--json]`（`file.export.colorLookupTables`、上流 file_cmds.rs の bake_cube）は、ページ N（既定 1）の見えている補正レイヤーを順に掛けた色の変わり方を .cube の 3D LUT（既定 33。`TITLE`・`LUT_3D_SIZE`・`DOMAIN_MIN/MAX`、小数 6 桁。環境のロケールに依らず小数点。256 まで書ける）に書く。出力が .cube ならそのファイル、フォルダーなら `p<NNN>.cube`。不透明度と `native.blend` は見て、マスク・クリップは見ない。補正レイヤーの無いページは恒等の表。式のまだ無い種類の層は省いて `skipped` に言う。`genko inspect <原稿> --looks`（`image.adjustments.colorLookup.list`）は作った見た目の一覧と、原稿の `color_lookup` の層（ページ・id・名前・表）を JSON で。
  - **画面**（利用者の決定 3: 画面で新しく作る補正は上流の形。`levels`・`curve` は `method: upstream`、明るさ・コントラストは `modern`、階調化は `floor`。既にある層はその層の形のまま直せる）: レイヤー → 色調補正 に 明るさ・コントラスト…・レベル補正…（Ctrl+L）・トーンカーブ…（Ctrl+M）・露光量…・カラールックアップ…・階調の反転（Ctrl+I）・階調化…・2 値化…・グラデーションマップ…・平均化（イコライズ）・自動トーン補正・自動コントラスト・自動カラー補正、ファイル → カラールックアップテーブルを書き出す…（印刷… の後の組。14 のコマンド。`app/adjust_forms_tone`）。**コマンドの名前（利用者の決定 8、2026-10-17）**: Photoshop と同じ名前にする。レイヤー → 色調補正 のコマンド（画素に掛ける）と、レイヤーパネルの「色調補正のレイヤー」で補正レイヤーを作る項目は、同じ補正なら同じ名前（`adjust_forms::command_title`: 窓の題と「…」。階調の反転は窓なしですぐ作る・掛けるので「…」なし。PC2b の色の補正も同じ。レイヤーパネルの Python の「色相・彩度・明度…」「色調反転…」は「色相・彩度…」「階調の反転」に）。同じ名前のコマンドは、コマンドを探す窓では名前の後に置き場所（メニューの道）を添えて出す（「レベル補正…　（レイヤー → 色調補正）」と「レベル補正…　（レイヤー → 塗り・グラデーション・色調補正のレイヤー → 色調補正のレイヤー）」）。クイックアクセス・コマンドバーの選ぶ窓・ショートカットの設定では、そのコマンドの名前を「レベル補正…（レイヤー → 色調補正）」のように置き場所を添えた名前にして区別し、その名前で覚える（クイックアクセスのボタンとツールチップもその名前）。同じ名前になる前に名前だけで覚えた設定（クイックアクセス・コマンドバー・キー）は、メニューで先にあるもの（前からその名前だったレイヤーパネルの項目）のものとして読む。GUI の試験の「窓のコマンドの名前は重ならない」（Python の決まり）は、この決定で「同じ名前なら、コマンドを探す窓に出る文（名前と置き場所）は重ならない」に変えた（test_gui_ledger_a・test_gui_workspace）。補正の窓: レベル補正は式・合成の欄・チャンネルの切り替え（組の空間のチャンネルごとの 5 つの数）・ヒストグラム・自動、トーンカーブは曲線の欄（上流の式ならスプラインで描く）とチャンネルの切り替え、カラールックアップは見た目の選択とファイルを読む（.cube・.3dl・.look）・補間・ディザ、グラデーションマップは逆・ディザ。パネル「色調補正」（種類のボタン。押すと上流の形の補正レイヤーを作り「属性」を出す）と「属性」（選んでいる補正レイヤーの不透明度・描画モード（`native.blend`）・ロック・種類の欄・既定に戻す。動かすと 250 ms でプレビュー、止めて 900 ms で 1 つの履歴として確定）。ウィンドウ メニューから出し入れする。

MCPの41道具・4リソース、CLI、HTTPの公開契約を維持する。外部プロセスから新しい`genko`実行ファイルを呼ぶ形とし、`python -m genko`という旧ランタイム呼出し自体は残さない。設定の実行パス更新は利用者確認付きで行う。

### COMP-04 既存Pythonプラグイン

既存`plugins.py`の`NAME/PARAMS/run(PIL画像)`契約を黙って廃止しない。ネイティブの拡張APIはC++本体と別プロセスの画像フィルターRPCとする。旧Pythonプラグインには同じRPCで接続する任意の外部互換ランナーを提供する。

Pythonは利用者が旧プラグインを有効にした場合だけ必要。本体・組込みフィルター・標準配布の必須依存にはしない。既定無効、利用者が選んだプラグインだけ実行し、依存がなければ日本語で理由を表示する。別プロセスはクラッシュ隔離であって安全なOSサンドボックスではないことを明示する。未保存原稿・認証情報を勝手に渡さない。

一覧表示のためにPythonファイルをimportしない。同意前はファイル名と非実行manifestだけを列挙する。明示選択・同意後に限り、そのプラグインのNAME/PARAMS取得を外部ランナーで行う。metadata取得にも時間・出力量の上限とクラッシュ処理を適用し、未選択ファイルのトップレベルコードを実行しない。

ネイティブの拡張（C++ 版だけ。2026-10-11 の利用者の判断で公開契約に加える。形式・RPC・断りは `docs/PLUGIN_NATIVE.md`）: 設定フォルダーの `plugins/<キー>/plugin.json`（プロトコル 1: `{"protocol": 1, "name": 文字, "executable": フォルダーの中の相対パス, "args"?: 文字のリスト, "params"?: PARAMS と同じ形}`）と、そのフォルダーの中のプログラムを、Python なしで画像フィルター `plugin:<キー>` にする。RPC は M3③の別プロセスの画像フィルター RPC と同じ（標準入力に 1 行の JSON `{"protocol": 1, "width", "height", "params"}` と RGBA の画素、標準出力に 1 行の JSON `{"ok": true, "width", "height"}` と同じ大きさの RGBA の画素、断りは `{"ok": false, "error"}`）。旧 Python プラグインと同じ規則に従う: 既定無効。一覧・名前・設定は plugin.json とプログラムのバイトを読むだけで何も起動しない。明示選択・同意（問いに動かすプログラムと引数を示す）の後だけ起動し、同意は plugin.json とプログラムの中身（sha256）に結び付け、変わったら選び直し。起動のたびに plugin.json とプログラムを読み直して選んだときと照らし、照らしたのと同じバイトを設定のフォルダーの中の本人だけが入れる一時フォルダー（`plugin-runs/run-…`。システムの一時フォルダーは noexec のことがあるので使わない）へ書き出して実行権を付け、その写しをシェルを通さず plugin.json の `args` だけで起動する（作業フォルダーもそこ。終わったら消す）。環境変数は旧ランナーと同じ短い一覧と `GENKO_PLUGIN_PROTOCOL=1`・`GENKO_PLUGIN_HOME`（元のプラグインのフォルダー）だけ。ハッシュが覆うのは plugin.json と本体だけで、同じフォルダーのほかのファイルは覆わない。写しを動かすので、本体の隣のライブラリは `$ORIGIN` などでは見つからない（`GENKO_PLUGIN_HOME` から探す）。時間（800 万画素ごとに 120 秒）と書き戻す量（画素のバイト数＋64 KB）の上限、落ちた・遅い・あふれた・起動できない・違う大きさの絵は日本語で知らせる。止めるとき、POSIX ではプラグインが始めたプロセスもまとめて止める（プロセスグループ。Windows ではプラグインのプロセスだけ）。標準エラーは最後の 64 KB を持つ。別プロセスはクラッシュ隔離であって安全な OS サンドボックスではない。同じキーの `<キー>.py` があるときは Python のプラグインを使う。

## 6. 追加する制作改善

### BRUSH-01 紙質画像

PNG/JPEG等を紙質として取り込み、原稿内素材として保持する。紙質の濃度、倍率、回転、反転、合成方式、適用座標を設定できる。ペン先画像と紙質は別項目。既定は紙面固定で、表示ズームにより紙質の物理サイズを変えない。

筆圧・不透明度との合成順序、乱数seed、継ぎ目方式を固定する。保存・再起動・別PC・Undo/Redo・印刷出力でも同じ線を再現する。紙質なしの既存ブラシは従来の意味を維持する。巨大画像・壊れた画像・アルファの扱いを検査する。

実装で確定した方式（M3）: 原稿の形式・合成順序・座標・seed（SplitMix64）・継ぎ目（繰り返し／折り返し）・画像の取り込み（白に重ねてグレー、縦横4096画素・64 MiBまで）・自分のブラシのライブラリ（Python版と共有する`brushes.json`には書かず`brush_papers.json`へ）は`schema-v4.md`「紙質（paper-texture@1）」と`native/src/render/paper.hpp`。解析可能な期待値fixtureと原寸基準画像は`native/tests/data/paper/`（`tools/migration/paper_reference.py`が独立に計算した期待値）。適用座標「線ごと」は線の id と最初の点から測るため、消しゴムで切った線は切れた所から紙目が新しく始まる（紙目を保つのは既定の紙面固定。線ごとの起点を切れた線へ持ち越すには線の形式の追加が要るため、M3 では行わない）。

### TEXT-01 ルビの詳細組版

- ルビ書体、本文に対するサイズ比、先頭/中央/末尾揃え、本文との距離、ルビ字間を編集できる。
- 絶対距離はmm、文字倍率は無次元で保存する。既定値未指定の旧原稿は現行の配置解釈を維持する。
- 親文字とルビの対応範囲を位置情報で保持し、同じ語が複数ある文章を誤指定しない。互換の`ruby_runs`入力は明示ルールで新しい範囲情報に変換する。
- 範囲はUnicode拡張書記素クラスタを単位とする半開区間[start,end)。採用Unicode版を固定し、UTF-16コード単位と混同しない。前方挿入は両端を移動、範囲直前への挿入は親文字へ含めず、範囲末尾への挿入も含めない。後方編集では対応を変えない。
- 親文字内部への挿入、部分削除、範囲をまたぐ置換、改行挿入は、機械的に読みを推測せず、そのルビを要確認にする。元の親文字・読みを保全して再割当/解除を選ばせる。親文字全削除ではルビを描画せず、Undoで本文とともに戻る履歴へ保持する。要確認のまま正式出力は停止する。全文置換にも同じ規則を適用し、IME未確定文字では確定データを変更しない。
- 禁則による行送りだけでは対応範囲を変更しない。重なり・はみ出しは警告し、無断で縮小・削除しない。
- 日本語IMEの変換中と確定後、Undo、全文検索置換、縦横切替、保存再開、PDF/PNGを試験する。

### PSD-01 編集可能な文字の受け渡し

PSD出力に「文字を編集可能なレイヤーとして保持」と「見た目優先で画像化」を明確に分ける。編集可能モードでは本文、縦横方向、フォント・サイズ・位置・色・必要な変形をPSD文字構造へ書き、画像層に見えるだけの台詞を文字レイヤー成功と数えない。

- 必須対応は縦横本文、改行、複数の部分書式run（フォント・サイズ・太字/斜体・色）、字間、段落揃え、平行移動・回転・拡縮、単色の縁取りと塗りを持つ効果文字。本文・ルビの文字列を編集可能に保つ。これらを未対応扱いして出力拒否/画像化した場合は未完成とする。
- 画像/グラデーションによる文字塗り、任意パス文字、非線形ワープ、特殊な多重縁などは、初版のPSD編集可能モードでは明示的に未対応としてよい。本体・PNG/PDF等の継承機能からは削らない。対応表を配布物に含める。
- 本文とルビは別の編集可能文字レイヤーに分け、同一グループと対応IDを付ける。フキダシは別層。PSD先で本文を変更した後にルビが自動追従する保証はしない。
- PSDで表現できない装飾・ワープ等は、対象と影響を出力前に表示する。「編集可能」指定のまま黙って画像化しない。厳密モードは出力を停止し、利用者が見た目優先を選んだ場合だけ画像化する。
- フォント不足や置換は警告。許諾なしにフォントファイルをPSDや配布物へ埋め込まない。
- 受取アプリでの再編集は利用者判断でwaived。ACCEPTANCE.md §6に従い、PSD文字構造とKrita読込を代替検査し、Photoshop/CSPでの再編集は未確認と明記する。購入・登録を行わない。

### UX-01 導入と最初の制作

Windowsはユーザー単位インストーラーとZIP、Linuxは対象環境で動く自己完結した配布物を用意し、Python設定なしで起動する。原稿を作る→コマを割る→線・台詞を置く→保存→開き直す→出力まで、日本語で案内する。手描きだけならAI設定を要求しない。

署名証明書未取得の場合は警告と配布元確認方法を説明し、「警告なし導入」を合格にしない。OSの保護解除・管理者権限付与を前提にしない。

設定の置き場所（M6、利用者の決定 2026-10-15「分けて初回に尋ねる」）: C++ 版は自分の設定フォルダー（Linux `$XDG_CONFIG_HOME/genko-studio` または `~/.config/genko-studio`、Windows `%APPDATA%\GenkoStudio`）に、環境設定（`settings.ini`）・最近の原稿・自作のブラシ・色・ポーズ・素材・オートアクション・AI 接続の鍵・プラグインを持ち、Python 版（`~/.config/genko`・`%APPDATA%\genko` と `QSettings("Genko", "Genko Studio")`）と並べて使える。初めて起動したとき、Python 版の設定があれば「引き継ぎますか？」と尋ね、はいのときだけ写す。写さないもの: 復旧用のコピー（`recovery/`）・キャッシュ（`cache/`・`thumbs/`・`fonts.json`）・プラグインの実行跡・ロック・書きかけのファイル。C++ 版にすでにある設定やファイルの上には写さない（中身の違うものは写さなかったと知らせる）。AI 接続の鍵は持ち主だけが読めるまま写し、新しいフォルダーは旧版のフォルダーと同じ権限で作る。リンクはリンクのまま写さない: ファイルへのリンクは指す先の中身を写し、フォルダーへのリンクは写さずに知らせる（C++ 版の変更がリンクを通って旧版のファイルに及ばないように）。旧版の設定は、あるかを確かめてから開く（Windows のレジストリは、無いキーを開くと作られるため）。同時に起動した二つのアプリが重ねて聞かないよう、新しいフォルダーのロックの下で聞く。Python 版の設定は読むだけで、変えず・動かさず・消さない。答えは一度だけ聞く（`migration/done`: copied・declined・none）。写せないものがあれば知らせ、次の起動でもう一度聞く（写せたものはそのまま）。`$GENKO_CONFIG_DIR` は従来どおりそのフォルダーを使い、引き継ぎは尋ねない（試験 `test_migration`）。引き継ぐかをまだ聞いていない間は、コマンドライン（`genko` のアプリ以外のコマンド、MCP を含む）が標準エラーにそのことを書く（AI 接続の鍵が見つからない理由が分かるように）。MCP の `inspect` の説明文は Python と同じ文のまま（プラグインの置き場所の例が旧版の場所。実際の場所は `inspect` の `plugins` が返す `folder`）。

### UX-02 画面と入力

### AI-01 接続の見える化

「未設定」「設定済み・未接続」「接続済み」「処理中」「人の確認待ち」「失敗」を区別する。設定コピー、対象クライアントの説明、テスト接続、原稿・会話の対応、最後の呼出しとエラー原因を画面から確認できる。

プロセスが起動しただけで「AIに依頼できた」と表示しない。接続テストは原稿を変更しない要求で行い、AI生成や課金を勝手に実行しない。外部クライアント設定の書換えは変更内容表示・バックアップ・利用者確認付き。トークン等を画面・ログ・配布証拠へ露出させない。

実装（M5④）: AI と作る の状態の一語と事実、テスト接続（`initialize`・`tools/list` だけ）、Claude Desktop と Hermes Agent の設定ファイルの変更案・写し・確認・取りやめ・元に戻す、原稿と会話の選択。Python との違いは COMP-01a の M5 の行。テスト接続が「接続済み」と言うのは Genko のサーバーが応答したことだけで、AI のアプリからつながったかは、AI が道具を使った記録（最後の呼び出し）で示す。設定ファイルへの書き込みは、安全に解けない形では書かずに理由を出す: Hermes の YAML で、一番上や mcp_servers・genko の中に鍵として読めない行（流れ形式の `{` `[`、明示の鍵 `?`、アンカー `&`・別名 `*`・タグ `!`、ブロックの `|` `>`、指示 `%`、`<<` の取り込み）があるとき、文書の区切りが二つ以上あるとき（先頭の `---` 一つだけは受け付けて残す）。Claude Desktop の JSON で、NaN・Infinity・1e400 のような数、64 ビットを超える整数、同じオブジェクトに同じ鍵が二つあるとき、UTF-8 でない（UTF-16 などは BOM から言う）とき。UTF-8 の BOM は読み飛ばして書き戻す。genko の項目を書き換えても、その後ろのコメントと空行は残す。「元に戻す」が今のファイルを残す写しは `.genko-before-undo-<時刻>` で、Genko の写し（`.genko-backup-<時刻>`）と分けるので、2 回押しても戻し直さない（今のファイルが写しと同じなら押せない）。Windows の Claude Desktop の設定ファイルは、Microsoft Store（MSIX）版の場所（`%LOCALAPPDATA%\Packages\Claude_*\LocalCache\Roaming\Claude\claude_desktop_config.json`）にフォルダーがあればそちらを先に見て、なければ `%APPDATA%\Claude\` を見る（既知の制限: Windows の実機では M6 で確かめる。パッケージ名の後ろの部分は決め打ちしない）。テスト接続は、原稿のフォルダーが無ければ何も起動せず、フォルダーも作らずに理由を出す。既知の制限（M6 の範囲）: Windows で genko:// のリンクを開くたびにコンソールの窓が一瞬出る（`genko app` を受け渡し役として起動するため）。AppImage で動かした Genko の「サイトのボタンで開けるようにする」は、一時的にマウントされた場所（`/tmp/.mount_*`）を登録してしまう（`$APPIMAGE` の場所を使うかを M6 で決める）。初めての設定から結果までの流れ（設定を書く → テスト接続 → 依頼 → 承認・返事 → AI が読み戻す）は、試験の代わりのサーバーと、この build の `genko mcp`（M5③。initialize は 2025-06-18。道具の記録 `studio/logs/tools.jsonl` と `studio/presence.json` を Python の genko/mcp/server.py と同じ形で書き、Python の読み手が同じに読む）の両方で通す。

## 8. APIと安全境界

### API-01 共通契約

GUI/CLI/HTTP/MCPは同じ権限判定・原稿モデルを使う。操作名、引数、dry-run、成功/失敗、画像応答、ジョブ状態、session、エラーコードを台帳化する。ヘッドレス動作にQWidgetやディスプレイ接続を要求しない。MCPのプロトコル版・能力交渉・取消・stderrログ・stdout汚染防止を実クライアントで確認する。

MCP道具数と編集op数は別物。MCPに公開しない人間専用opを、移植時に一括公開しない。文頭の古いコメントではなく現行の`record_chat_approval`を含む実装・ゲートを引き継ぐ。

### API-02 権限と入力防御

actorの`human:`/`ai:`、固定欄、ページロック、承認、session間の干渉防止、他者変更のUndo拒否を維持する。チャット承認は本人の明示意思と原稿側の許可があるときだけ記録でき、停止設定をAIが解除できない。

HTTPは既定でループバック、`/health`以外の認証、Host/Origin検査、root以下へのパス制限を維持する。要求内の素材・フォント・ZIP・シンボリックリンク・URL・外部コマンドにも検証を適用する。HTTP本文上限の現行64MiBを維持し、展開後寸法・圧縮爆弾・深いJSONにも別の上限を設ける。許可されないパスを正規化だけで承認しない。

生成AIクライアントやアップスケーラーの認証方式、課金先、許可コマンドを変更しない。原稿・ログを外部へ自動送信しない。

## 9. 性能と完成条件

### PERF-01 測るもの

性能はC++製品が`ACCEPTANCE.md`の絶対基準を満たすかで判定する。Python版との倍率競争や比較版開発は行わない。起動、入力→表示、線確定、Undo/Redo、ページ切替、保存中の応答、出力完了、メモリを別に測る。

最終ゲートは、全機能台帳の移行済み・受入成功、旧原稿の無損失変換、保存障害と復旧試験、実ペン/IME、PSD文字の実受渡し、全出力、CLI/HTTP/MCP、Windows/Linuxの配布物、性能基準、ライセンス、利用者課題完走が揃うこと。ただし実ペン、Windows実機のペン/IME、PSD受取アプリでの再編集、利用者課題、利用者の外部クライアントでの初回導入は、利用者の判断（2026-10-02）で実施不要とし、`ACCEPTANCE.md` §6の代替検査で置き換える。代替検査を元の試験の合格とは呼ばない。
